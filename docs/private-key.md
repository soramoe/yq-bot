# 私钥与签发规范

> 这份文档是操作规范，不是法律文件。目的是让「卖授权」这件事在工程上不出事：
> 私钥不丢、不泄、不混进发布物；出问题时知道怎么换、怎么补。

## 0. 先认清威胁模型

- Node 是明文，客户端在用户手里，**任何人都能改代码绕过授权**。这是接受的前提。
- 私钥一旦泄露，别人就能签出和官方一模一样的授权文件，而且离线授权**无法远程吊销**。
- 所以私钥的目标不是「防住所有人」，是「不因为自己的疏忽把签名能力送出去」。

## 1. 密钥放在哪

| 东西 | 位置 | 是否进仓库 |
| --- | --- | --- |
| 私钥 | `C:\Users\<你>\.yuqing\license-private.pem` | ❌ 永不 |
| 公钥 | `server/core/license.mjs` 的 `LICENSE_PUBLIC_KEY` | ✅ 本来就要公开 |
| 本机授权 | `data/license.json` | ❌（`data/` 已 gitignore） |
| 客户授权 | 客户自己的 `data/license.json` | ❌ |

私钥文件权限尽量只给当前用户；Windows 上右键 → 属性 → 安全 → 只保留自己。

## 2. 生成新密钥

```bash
node server/tools/license-keygen.mjs
```

它会：

1. 在 `~/.yuqing/license-private.pem` 生成 Ed25519 私钥；
2. 打印公钥 base64；
3. 把公钥填进 `server/core/license.mjs` 的 `LICENSE_PUBLIC_KEY`；
4. 重新跑自检、发版。

已有私钥时脚本会拒绝覆盖。**换密钥等于旧授权全部失效**，确认要换再加 `--force`。

## 3. 签发

日常用签发台：

```bash
签发授权.bat
```

它只监听 `127.0.0.1:8910`，填客户机器码、uid、天数，生成 `license.json` 给对方。
命令行等价：

```bash
node server/tools/license-issue.mjs --machine <64位机器码> --uid <B站uid> --customer "客户名" --days 365 --updates-days 365
```

注意事项：

- 签发台**不要**改成 `0.0.0.0`，不要暴露到公网，不要放在有公网 IP 的机器上。
- 签发用的电脑尽量干净：全盘加密、锁屏密码、不装远程控制软件。
- 私钥不要通过聊天工具、邮件、网盘传输。要换机器就用加密 U 盘离线拷。
- 不要在 CI 里签发，也不要把私钥放进 GitHub Secrets。CI 只负责构建和发版。

## 4. 备份

- 至少两份离线备份：加密 U 盘 / 离线硬盘 / 密码管理器附件。
- 不要放在 OneDrive、iCloud、坚果云等会自动同步的目录。
- 备份文件加密码（7z/age/gpg 都行），密码单独记。
- 备份里同时放一份公钥和「当前版本号」，方便以后确认哪对密钥对应哪个版本。

## 5. 换密钥（轮换）

什么时候换：私钥可能泄露、电脑送修/丢失、你要把签发权交给别人、或者只是定期轮换。

步骤：

1. 停掉签发台，确认没有正在进行的签发。
2. `node server/tools/license-keygen.mjs --force` 生成新密钥。
3. 把新公钥填进 `server/core/license.mjs` 的 `LICENSE_PUBLIC_KEY`。
4. 跑全量自检，发一个新版本（例如 1.0.2）。
5. 给还在有效期内的客户**免费重签**一份新授权；旧授权在新版本上会显示 `invalid`。
6. 旧私钥不要立刻删，离线封存至少一个续费周期，用于核对历史签发记录。

> 当前代码只支持**一个**公钥。如果以后要平滑轮换，需要把
> `LICENSE_PUBLIC_KEY` 改成数组，验签时逐个尝试；这属于后续改动。

## 6. 私钥泄露了怎么办

1. 立刻换密钥（第 5 节），发新版本；
2. 在 README / 群里发公告，说明旧授权将失效、如何换新；
3. 检查签发记录，列出可能被冒签的客户；
4. 如果私钥进过 git 历史，`git log --all -- '*.pem'` 确认，然后重写历史并强推；
   但**重写历史不等于收回**，拿到过的人仍然有，必须换密钥；
5. 保留证据，必要时走法律途径。

## 7. 禁止清单

- ❌ 把 `*.pem`、`*.key` 提交进 git
- ❌ 把私钥贴进聊天、issue、PR、日志
- ❌ 把私钥放进 GitHub Actions Secrets 或任何云端 CI
- ❌ 在公网机器上跑签发台
- ❌ 用同一份授权给多台机器/多个账号
- ❌ 把「测试用」的私钥和正式私钥混用

## 8. 定期检查

```bash
# 仓库里有没有意外提交的密钥
git log --all --oneline -- '*.pem' '*.key'

# 当前工作区有没有 pem
git ls-files '*.pem' '*.key'
```

`.gitignore` 已包含 `*.pem` / `*.key`，但 ignore 挡不住 `git add -f`，还是要靠检查。
