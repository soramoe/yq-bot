# 决策记录

> 只记已经拍板的事。每条都写清**为什么**，否则三个月后没人记得原因。
> 未拍板的放文末「待定」。

---

## D1 · 三代是重写，不是演进

**决定**：在 `E:\渔月崽三代` 独立开发，不修改二代，两边不共享代码。

**为什么**：二代线上跑着真实用户在用的机器人。任何"边跑边改"的重构都会把稳定性风险
转嫁给正在直播的人。重写允许一次到位地换掉地基，且随时可以放弃。

---

## D2 · 日志是事实，统计是投影

**决定**：所有事件先 append 到日志，再分发给插件。统计数字由 `reduce(日志)` 得出。

**为什么**：二代"内存 metrics + 30 秒落盘"导致直播中重启丢整场，恢复逻辑退化成
一堆"条件不匹配就拒绝"的猜测。日志投影让恢复变成"重放"，不需要猜。

**推论**：禁止任何"内存里累加、定时保存"的统计实现。

---

## D3 · 插件分两类，判据三问

**决定**：内核管规矩（闸门、模板、冷却、日志、状态机、配置），插件管玩法（欢迎、答谢、盲盒…）。

**判据**：
1. 关掉它机器人还能跑吗？不能 → 内核
2. 有人只想要一半吗？会 → 独立插件
3. 要能一秒钟关掉吗？要 → 独立插件

**为什么**：二代把 `console`（全局闸门）做成了插件，于是 dryRun 有了两个真相，
必须写 `effectiveDryRun()` / `setDryRunEverywhere()` 去对齐。层放错的代价是持续打补丁。

---

## D4 · 总控制台下沉内核

**决定**：`console` 的能力（总开关、演练模式、免打扰、发送时机）成为内核的发送闸门，
不再是一个插件。

**为什么**：所有插件和内置 AI 都要经过它。把"所有人共用的规矩"做成"可插拔的玩法"，
必然导致重复判断和状态不一致。

---

## D5 · 高级欢迎并入欢迎

**决定**：`welcome-pro`（荣耀/舰长/主动@）与 `welcome`（普通进场）合并为一个插件，
内部拆成 `honor.mjs` / `guard.mjs` / `greet.mjs` 三个模块。

**为什么**：两个插件在抢同一个进场观众，各有一套冷却、各有一套"这个人归谁"的判断，
二代只能靠配置互读 + `reenterSec` + `burstGuard` 打补丁。

**同一业务拆成两个插件，是插件化过度的典型症状。**

---

## D6 · 喊话并入定时播报

**决定**：`shout`（按间隔发弹幕）不再独立，作为「定时播报」的一种模板来源。

**为什么**：两者都是"开播期间按时间发文本"，分开会重复实现频率控制与免打扰判断。

---

## D7 · 入口拆薄，路由表驱动

**决定**：`server/main.mjs` 只做装配（目标 100 行内），路由按领域拆到 `server/routes/*.mjs`，
用表驱动匹配，不引 HTTP 框架。

**为什么**：二代 3775 行里 54 个手写 `if (pathname === ...)`，匹配顺序成了隐式依赖，
加接口时容易插错位置，且无法一眼看全 API 面。

---

## D8 · 前端不引框架，用 schema 驱动表单

**决定**：原生 ESM + `// @ts-check` + JSDoc。配置界面由插件 manifest 的字段声明自动生成。

**为什么**：这个产品的前端 80% 是配置表单。手写 40 多个开关是把人力花在重复劳动上，
且每加一个配置项就要改渲染代码 —— 二代 9655 行的主要来源之一。

**验收**：新增一个插件，前端代码改动 = 0 行。

---

## D9 · 不引 Tailwind 或 UI 框架

**决定**：样式走自建 tokens（字号 4 档 / 字重 2 档 / 间距 6 档）+ 四条 Grid 布局规则。

**为什么**：
1. 零构建是本地工具的优势，不该为布局破掉
2. Tailwind 的 JIT 靠静态扫描，而本项目大量动态拼接 class（`'card ' + state`），
   会被漏扫，只能靠 `safelist` 手动维护 —— 等于再养一份"必须同步的清单"
3. 要解决的"乱"是缺约束，不是缺工具；约束自己写 6 个变量就有

---

## D10 · 两种更新模式必须分开

**决定**：配置页用 `snapshot → 重渲染`；监控页（事件流/日志）用 `event → append → 合并渲染`。

**为什么**：二代把两种模式混在一个 `pushEvent` 里，导致补发 60 条被"每秒 3 条"限流
吃掉 57 条，只能再加一个旁路分支。**限流应放在渲染层，不该放在入库层。**

---

## D11 · 搬家和改行为，不在同一步做

**决定**：P0–P2 阶段，用户可见行为必须零变化；P3 起才改观感，P4 起才加功能。

**为什么**：一旦搬家（改结构）和改行为混在一起，出问题时无法判断是"搬错了"还是"改错了"，
回退也会连带丢掉已完成的改动。

---

## D12 · 事件模型先规范化，再接协议

**决定**：内核只认规范化事件类型（`DANMAKU` / `GIFT` / `GUARD_BUY` / `ENTER` /
`LIVE_START` / `LIVE_END`），B站原始报文在适配层转换。

**为什么**：协议细节会变（二代已踩过"连击两种报文"的坑）。把协议差异挡在适配层，
内核与投影的测试就可以完全离线跑，不需要连真房间。

---

## D13 · 授权等到 P4 之后

**决定**：在拿到至少 3 个真实用户之前，不做授权、不做注册。

**为什么**：功能还没值钱时做防盗版，只会先把自己的用户挡在门外。

## D14 · 不做的事

| 不做 | 原因 |
|---|---|
| 多平台（抖音/快手） | 协议维护成本吃掉全部利润 |
| 云托管跑机器人 | 账号安全 + 成本双重风险 |
| 团队协作 / 复杂权限 | 单主播场景用不上 |
| 自动抽奖、自动私信、自动关注 | 风控严，出错即资损或封号 |
| 数据库 | 一场几千条事件的量级，JSONL + 快照投影足够 |

## D15 · 二维码自己编码，不引 qrcode 依赖

**决定**：`server/qr/` 自实现二维码编码（字节模式、纠错 M、版本 1–10），
用 SVG 直接内联进页面，同时在终端渲染一份。

**为什么**：

1. 登录是必经路径。依赖 CDN 或额外二进制意味着"某个环境里扫不了码"，
   而这种失败只会在用户第一次登录时暴露
2. 不值得为一个 400 行的确定算法引包 —— 它没有版本迭代风险，标准 2006 年就冻结了

**正确性保障**：`check-qr` 拿二代项目里的 `qrcode` 库当对照，
10 个版本 × 8 个掩码共 80 组，模块矩阵**逐位比对**。
另外单独验证"自动选版本/自动选掩码"的结果与参照实现一致。

**已知代价**：只支持字节模式，不做字母数字/数字模式优化。
纯大写字母数字内容可能比最优编码大一个版本 —— 登录 URL 含 `?` `=` 等字符，
本来就走字节模式，不受影响。

## D16 · 凭证原子写，脱敏只有一个出口

**决定**：

1. `data/auth.json` 先写 `.tmp` 再 `rename`
2. `redactCookie()` 是全项目**唯一**允许把 Cookie 变成可显示文本的函数，
   日志、错误、诊断包一律走它
3. 对外接口（`status()`）的结构里根本没有 `cookie` 字段

**为什么**：

- 直接覆盖写，一旦在写一半时断电，下次启动就是"凭证文件损坏"，
  表现是"莫名要重新扫码"——这类失败只在关机/崩溃后出现，最难联想到原因
- 日志里出现一次 SESSDATA 明文，等于把账号交出去。而日志是最容易被
  复制、粘贴、发到群里排查的东西

**自检**：`looksLeaked()` 会扫描响应体和日志摘要，确认搜不到原值。

## D17 · 登录服务只认本机 Host

**决定**：登录服务绑定 `127.0.0.1`，并校验 `Host` 头必须是
`127.0.0.1:<port>` / `localhost:<port>`，否则返回 403。

**为什么**：防 DNS 重绑定。恶意页面把自己的域名解析到 127.0.0.1 后，
浏览器会认为请求同源，从而能读到本机接口的响应 —— 而本机接口里有登录态。

**副作用**：用局域网 IP 访问（比如手机连电脑 IP 看登录页）会被拒绝。
这是有意的：登录页必须在本机打开。

## D18 · 唯一的外部依赖是 `ws`

**决定**：协议层用 `ws` 连弹幕长连，其余全部用 Node 内置模块。
二维码、protobuf、WBI 签名、二进制拆包、HTTP 封装都是自己实现的。

**为什么破例**：B站 弹幕长连**必须带 Cookie**（不带会被当游客，
约 5 分钟后把用户名打码成 `X***`、uid 归零），而 Node 内置的
`WebSocket` 不支持自定义请求头 —— 这是 Node 的已知限制，没有绕法。

为什么不像二维码那样自己写：WS 客户端要处理帧掩码、分片、控制帧、
TLS 复用、关闭握手。它是**有状态且与对端强耦合**的协议，自写出来的 bug
表现为"偶发断连""某些房间连不上"，排查成本远高于一个成熟的 3MB 依赖。
二维码是确定算法、无 IO，两者不可类比。

**代价**：首次运行需要 `npm install`（一个包，无子依赖）。
这是全项目唯一需要联网安装的环节。

---

## D19 · 金额统一用「电池」，换算只在适配层做一次

**决定**：B站 报文里的金额是**金瓜子**，`normalize` 里统一除以 100 换算成
**电池**（1 电池 = 0.1 元）后，才写入事件。内核、投影、插件只看电池。

**事件里同时带 `price`（单价）和 `battery`（总价）**：
- 展示单价时用 `price`（可能是小数，如 1/3 电池）
- 统计求和**必须**用 `battery`

**为什么**：B站 的 `total_coin` 是本次总价，直接拿 `total_coin / num`
得到单价会除不尽，四舍五入后 `price × num ≠ total`。
二代因此出现过"统计和对账差零点几"，属于最难查的一类 bug。

**代价**：`price` 不是整数，UI 展示时要自己决定保留几位小数。

## D20 · 状态机三态：offline / live / live_unknown

**决定**：房间状态不再是两态，而是三态。`live_unknown` 表示
「有事件在来，但没收到过 `LIVE_START`」—— 也就是场次起点不确定。

**为什么**：审计发现，隐式场次（进程在直播中途启动）原先把状态直接设成 `live`，
于是后面真正的 `LIVE_START` 到来时「当前已是 live」不产生边沿，
**两场数据被合并成一场，全程零报错**。这类错误只在
「直播中重启」这一种时序下出现，正常测试永远测不到。

三态把这个区分显式化：`live_unknown → live` 是一次真实的状态转变，边沿照出。

**代价**：状态名字多了一个，凡是用 `state === 'live'` 判断"是否在播"的地方
必须改成 `state !== 'offline'`。对外快照同时提供 `hasKnownStart`，
避免调用方自己拆状态。

---

## D21 · 幂等靠 seq，不靠"当前状态"

**决定**：状态机只负责语义（这次开播是不是新的一场），**不负责去重**。
去重由 seq 保证 —— 同一个事件喂两遍，投影第一道判断就挡住了。

**为什么**：二代用 `if (st.liveOn) return` 这类"看当前状态"的方式做幂等，
问题是它分不清「重复推送的同一场」和「真的又开了一场」。
三代改成：`LIVE_START` 用 `liveTime` 识别重复 —— 有 `liveTime` 时严格比对，
没有时保守认定为重复（代价是多一场空场次，而不是丢一整场数据）。

**代价**：`liveTime` 缺失时，两场紧挨着的直播可能被合并。
这是有意选择的方向：**宁可多算一场空的，不可少算一场真的。**

---

## D22 · 发送闸门在内核：插件只能请求说话，不能决定是否说话

**决定**：dryRun、最小间隔、内容去重、发言记账，四项全部在
`server/core/gate.mjs`。插件拿到的是一个 `say()` 请求接口，没有别的入口。

**为什么**：二代把总控制台做成插件，于是"要不要发"有两个地方能改，
最后长出 `effectiveDryRun()` / `setDryRunEverywhere()` 这类补丁，
还要在 `/api/status` 里回传 `dryRunMismatch` 告诉用户两处不一致。
**一件事有两个写入点，就一定会不一致。**

**两个附带决定**：

1. **演练模式也占用时间槽和去重窗口**。否则演练时一路顺畅、
   正式上线立刻被限速打脸，演练就失去了意义。
2. **未知错误码按 fatal 处理**。风控码的典型形态正是"没见过的新码"，
   把它当可重试，等于在最该停下来的时刻继续按节奏发。
   确认某个码只是临时问题后，加进 `RETRY_CODES` 白名单。

**代价**：插件不能自己做"重要的话插队说"。需要插队的场景
（比如舰长上舰）由内核留出的优先级参数解决，不给插件开后门。

## D23 · 入口只做装配，业务一律往下沉

`server/main.mjs` 保持在一百多行，只有三件事：解析参数、装配、处理退出信号。

二代 `index.mjs` 3775 行的成因不是一开始就乱，而是"先写在这里，以后再搬"。
这个"以后"永远不会来。所以三代定死：**入口出现任何业务分支，就算是设计走偏**。

路由同理：`api.mjs` 是一张表，`router.list()` 能把 6 条路由一次打完。
二代的 54 个 `if (pathname === ...)` 只能靠全文搜索，还隐含了匹配顺序依赖。

## D24 · WebSocket 必须"先订阅，再取快照"

补发的顺序是：订阅生效 → 取 backlog → 发送 → 把订阅期间攒下的事件按序补上。

反过来（先取快照再订阅）有一个几十毫秒的窗口，落在窗口里的事件**永久丢失**，
而且丢得毫无痕迹 —— 页面照常刷新，只是少了几条。

这条有断言盯着：`check-http` 里那个"取快照期间到达的事件不能丢"的用例，
就是让 `recentEvents()` 在被调用的同时广播一条事件来复现这个竞态。

**代价**：连接初期会多一次内存排队。相对"静默丢事件"，这个代价可以忽略。

---

## D25 · 补发不连续时必须说"有缺口"

缓冲上限 5000 条，断得太久就只能给最近的。这时 backlog 带 `gap: true`。

**绝不把不连续的两段接起来装作连续。** 二代的"事件流停在 20:47"
表面上是限流问题，本质是"页面不知道自己缺了东西"，所以没人发现。

前端拿到 `gap` 会弹一条提示，写明从哪个 seq 开始补。

---

## D26 · 前端数值一律左对齐，不做"右对齐到面板边缘"

侧栏的 `键 → 值` 一开始是 `space-between` + 右对齐，结果在某些宽度下
整列值跑到容器外面：DOM 里文字在、`getBoundingClientRect` 也正常，
但屏幕上看不见 —— 表现和"数据没来"一模一样，极难排查。

改成"标签固定 68px + 值左对齐"之后，这个故障类别从结构上消失。
**能左对齐就不要右对齐**：右对齐的收益是好看，代价是一次算错就看不见。

---

## D27 · 页面不用 innerHTML

页面显示的内容全部来自外部（弹幕文本、昵称、礼物名），是不可信输入。
统一用 `textContent` 构造节点，XSS 在结构上就不可能发生，
不需要依赖"记得转义"。

**代价**：构造节点的代码比模板字符串长。这是值得付的。

---

## D28 · 插件"不播就 return false"，不许自己判断别人会不会播

二代的礼物答谢插件想知道"盲盒插件会不会也播报这个礼物"，于是**直接读盲盒插件的配置**，
自己复算一遍 `minProfit`。三个后果：

1. 两个插件的配置谁先改都会让判断失效；
2. 盲盒插件改了过滤逻辑，答谢这边毫不知情；
3. 它只静态复算了 `minProfit`，**冷却没算** —— 于是「minProfit=10 且这盒只赚 3」
   或者「同一人冷却中」时，盲盒不吭声、答谢让了路，**观众花了钱一条反馈都看不到**。

三代的规则只有一条：

> 只有**真的要播**的时候才 `return true`（认领）。
> 不播就 `return false`，让低优先级的插件接手。

于是"是否播报"和"是否让路"永远是同一个判断，不可能再错位。
优先级只写在 manifest 的 `claims` 里（盲盒 200 > 答谢 100），插件之间零引用。

**这条有回归用例**：`check-gift` 的「亏了且低于门槛 → 让路给礼物答谢」。

## D29 · 连击数量用 comboCount 的差值，不用 num 累加

B站 客户端把连击攒着发，同一个人送 5 个，服务端可能只推过来 3 条报文。

- `num` 是**这一条**的数量；
- `comboCount` 是**到此为止一共几个**。

所以数量 = `comboCount` 的增量，而不是 `num` 相加。累加会得到 3，而观众送的是 5 ——
统计里是 5 个、答谢里写「×3」，对不上，而且不报任何错。

同一条规则还管金额：单价 = 总价 ÷ 数量，补数量时按同一单价补金额，
否则「×5 · 3 电池」两个数会各自算各自的。

拿不到 `comboCount`（或它没变大）时才退回 `num` 累加 —— 这是新的一波连击。

---

## D30 · 答谢的顺延必须有上限

连击合并靠"到期才发"。观众一直送就一直顺延，会把「×2 ×3 … ×50」攒到几十个
才憋出一句 —— **答谢迟到比不答谢更奇怪**。

所以 `deadline = min(第一次到期 + maxWaitSec, 本次到期)`，超过封顶立刻发一次，
再开始攒下一批。

顺延规则是纯函数（`_merge`），自检直接调它断言 deadline，
不靠 `sleep` 卡时间 —— 时间相关的断言一旦依赖真实时钟，早晚会变成随机失败。

## D31 · 待发答谢只放内存，**故意不落盘**

事件日志是事实，重启要能重放。但"待发答谢队列"不是事实，是**中间状态**：
写进日志后重启重放，会变成重复答谢 —— 那比漏一句更糟。

所以 pending 只在内存里，进程退出即丢弃，并在停止时打一行日志说明丢了几条。
**能安全丢弃的中间状态，就不要让它进入事实层。**

## D32 · 闸门允许"高优先级等一个槽位"，但绝不做队列

真实房间跑起来才发现的：进场欢迎每秒一条就能把最小间隔（1200ms）占满，
于是礼物答谢几乎永远发不出去。闸门只把 `blockedInterval` 加一，
**页面上看不出任何异常**，日志里也没有一行 —— 观众花了钱，一条反馈都没有。

修法不是"给礼物开绿灯"（那就等于取消限速），而是：

> `priority > 0` 的消息，**只因为间隔不够**被拦时，可以等一个槽位（最多 `maxWaitMs`）。
> 去重拦下的不等 —— 等完还是同一句话，白等。

三条边界写死在闸门里，插件只能声明"我愿意等"，不能决定"我可以插队"：

1. **只重试一次**，重试时 `maxWaitMs = 0`。否则闸门就变成队列了，
   而队列会把"限速"悄悄变成"延迟"，问题从"发不出去"变成"两分钟后才发"。
2. **等不起就不等**：需要等的时间超过上限时，一开始就放弃，不做无意义的挂起。
3. **低优先级不排队**：一次进场欢迎不值得为它等，直接丢。

计数器多两个：`waited`（等到了）和 `gaveUp`（等了也没等到）。
`gaveUp` 长期不为 0 说明限速配得比房间的活跃度还紧，该调 `minIntervalMs` 了。

## D33 · 缺口有两种，只判一种就会重演"事件流少一截"

补发最多一次给 800 条。以前判断"有没有缺口"只看一种情况：

> `after` 比缓冲里最早的还早 → 标 `gap`（要的那段已经被滚出缓冲）

漏掉的是第二种，**而且它才是常态**：

> 一次没给完 —— 取到 800 条上限，而后面还有更新的

断线几分钟就会超过 800 条。于是"补了 800 条、剩下 2000 条悄悄丢掉"
在页面看来是连续的：数字照跳（来自每秒推送），事件流少一截，没有任何提示。
这正是二代"事件流停在 20:47"的同一个病根。

现在 `gap = (after < oldestSeq - 1) || (to < latestSeq)`，并且把 `latestSeq`
一起返回，前端提示能说清"还差多少条"。

**教训**：判断"数据是否完整"时，光看下界不够，要同时看上界。

## D34 · 插件上下文 `ctx` 里不要用对象字面量的 `this`

`_ctx()` 返回的是对象字面量，里面的 `get state()` 是**方法**，
其中 `this` 指向这个 ctx 对象，不是宿主。原来的写法：

```js
get state() {
  return typeof this.getState === 'function' ? this.getState() : null
}
```

`this.getState` 永远是 undefined（ctx 上没有这个方法），于是 **`ctx.state` 恒为 null**。
后果是安静的：所有 `ctx.state?.roomId` 都拿到 undefined，
欢迎插件的冷却键、礼物合并键里的房间号全部为空 —— 单房间跑起来完全正常，
一开第二个房间才会开始串数据。

修法是显式捕获 `const host = this`，并且在自检里加一条断言直接读 `ctx.state`。

**教训**：`?.` 链会把"缺一个对象"和"这个字段本来就没有"变成同一种表现。

## D35 · 对账要和"快照那一刻"对齐，否则会误报

对账是两边比：日志逐条累加 vs 投影快照。但读日志和取快照之间有一小段时间，
直播中每秒都有事件进来，快照会比日志**多**几条 —— 对账于是报"差几条"。

那种误报最伤：一旦对账会无缘无故失败，真出问题时没人会当回事。

所以 `upTo(snapshot, events)` 先把日志裁到 `seq <= snapshot.lastSeq` 再比。
两边必须是同一个瞬间，才算得上"对账"。

## D36 · 醒目留言的 `price` 是元，不是金瓜子

**决定**：`normalizeSuperChat` 不再调用 `toBattery()`，改用报文自带的 `rate`
（每元多少金瓜子，实测 1000）换算：

```
battery = price(元) × rate ÷ 100(金瓜子/电池)
```

`rate` 缺失时退回「1 元 = 10 电池」。payload 里同时给出 `yuan`（元）和
`battery`（电池），文案用 `yuan`，统计用 `battery`。

**为什么**：礼物、上舰的报文金额是金瓜子，SC 的是元。原来一律套 `toBattery()`
（÷100），于是 **100 元的 SC 被算成 1 电池 = 0.1 元，差 1000 倍**。

这个错误安静得可怕：不抛异常、不影响对账（两边都用同一个错值，一致性照样成立），
只是金额栏显示 `¥0.1`，统计里全场最花钱的那类收入接近 0。

**怎么发现的**：日志里一条 SC 是 `duration: 300, battery: 1`。
B站 的置顶时长由金额决定（100 元 = 300 秒），所以真实金额是 100 元，
而 `1` 恰好是 `100 ÷ 100` —— 单位错了才会出现这种"整数巧合"。

**代价**：旧日志里的 SC 金额是错的，且**不改写**。日志是事实（D2），
事后修改历史会让"重放能复现"这件事失效。旧数据就让它错着，新数据是对的。

## D37 · SC 不合并、不冷却 —— 和礼物答谢正好相反

| | 礼物答谢 | 醒目留言答谢 |
|---|---|---|
| 合并 | 必须合并（连击会刷满弹幕） | **绝不合并** |
| 冷却 | 同一人有冷却 | **没有冷却** |
| 优先级 | 1，最多等 3 秒 | 2，最多等 5 秒 |

**为什么**：SC 是观众**花钱买了置顶**的，一条就是一条。合并成
「感谢 A、B 的醒目留言×2」等于把两个人各付一次的钱合成一次答谢 ——
观众不会怪机器人，只会觉得主播没看见他。

**已知取舍**：同一人连发两条同额 SC，文案完全相同，第二条会被闸门的内容去重拦下。
这不是 bug，是 D22「插件不能给闸门开后门」的必然结果。拦下时插件写一条 info 日志，
不静默吞掉 —— 「以为回了、其实没回」是最难发现的那类问题。

## D38 · 关注答谢并入欢迎，不新建插件

**决定**：`FOLLOW` 由 `welcome` 插件认领，与 `ENTER`、`GUARD_BUY` **共用一张冷却表**。
三条路径合并成一个 `_greet(ctx, ev, {template, reason})`。

**为什么**：
1. 关注、进场、上舰都是「人来了」的语义，共用冷却、共用模板变量。
   拆成三个插件就会重演二代 `welcome` / `welcome-pro` 抢同一批观众的老问题（D5）。
2. **共用冷却表是必须的**：B站 在关注后常常再推一条进场，两条各自判冷却会连发
   「感谢关注」+「欢迎来到直播间」。共用一张表时，先到的那条说、后到的那条被挡住，
   两种顺序都只发一句。

**代价**：关注和进场只有一句会被说出，另一句的信息就丢了（先进场的人听不到"感谢关注"）。
用「少说一句」换「不刷屏」，这个取舍是明确的。

## D39 · 花钱的每一类事件都必须有认领方

**决定**：`GIFT`（礼物）、`SUPER_CHAT`（醒目留言）、`GUARD_BUY`（上舰）
这三类「观众花了钱」的事件，**必须**在某个插件的 `claims` 里出现，并有用例盯住。

**为什么**：`SUPER_CHAT` 曾经没有任何插件认领 —— 30 元起步的醒目留言
一句回应都没有，不报错、不计数、不在界面上留任何痕迹。
这直接违反 P1b 的验收线「观众花了钱就一定有反馈」。

**判据**：加新事件类型时，先问一句「这个事件有没有人管？没人管时会不会有人吃亏？」
如果答案是"会"，就必须有认领方，哪怕只是一句「收到」。

## D40 · 配置只存增量，不存整份

**决定**：`data/app.json` 的 `plugins` 段只记录**用户动过的键**：

```json
{ "plugins": { "welcome": { "template": "嘿 {用户}" } } }
```

不是 `{ "plugins": { "welcome": { 全部 8 个字段 } } }`。

**为什么**：存整份 = 用户第一次点开面板的那一刻，所有默认值被固化成"他的设置"。
此后插件升级改了默认文案，老用户永远看不到新文案，而且**没有任何提示** ——
界面上显示的每一项都叫"已保存的设置"，看起来完全正常。

这类问题特别难发现：它不是坏了，是"永远停在第一次打开的那天"。

**代价**：用户把一个字段改回和默认一样的值，增量里会留一个等于默认的值，
之后 manifest 改默认就不跟随了。可接受 ——「恢复默认」会把整条删掉。

## D41 · 「插件停用」与「功能关掉」是两个开关

**决定**：
- **宿主级** `pluginEnabled: { id: false }`：这个插件完全不参与认领
- **插件级** `config.enabled`：这个插件的业务功能开不开

两者都在界面上，位置不同（前者在插件标题右侧，后者在配置区里）。

**为什么**：如果只有一个开关，用户停用一个插件时，我们只能二选一：
改掉他的配置（再启用时设置没了），或者不动配置（停用期间看起来配置是"开"的）。
两种都会让人困惑。

**顺带**：重新启用时**把键删掉**，而不是存 `true`。存 `true` 会让
"以后默认关掉这个插件"这种改动永远生效不了 —— 又是一次"设置停在旧版本"。

## D42 · 免费礼物的金额记 0，但个数照算

**决定**：`isPaid === false` 的礼物（银瓜子/免费）：
`giftCount` 照加，`giftBattery` 加 0。判据是 `isPaid === false`
而不是 `isPaid === true` —— 老日志没有这个字段，缺省按付费算，
否则升级后历史礼物金额会整片归零。

**为什么**：银瓜子的免费礼物（小心心一类）报文里**也带 `total_coin`**，
直接累加会让「本场收入」凭空多出几块几毛。

**为什么对账查不出来**：两条计算路径读的是同一个字段，错得一模一样，
一致性照样成立。这正是"双算对账"的边界 ——
它保证两段代码算得一样，不保证这个算法符合业务含义。
所以这条只能靠人发现，并且必须在 projection 和 sum 两处同时改，否则从此每次启动都报差异。

## D43 · 配置即时生效，没有「保存」按钮

**决定**：字段 `change` 即保存，没有保存/取消按钮。改动后立刻生效，不需要重启。

**为什么**：
1. 加了保存按钮就多一个状态：「界面上是这个值，实际生效的是另一个值」。
   用户关掉页面时不会记得自己有没有点保存。
2. 配置项都是独立的小值，没有"必须一次改完"的原子性需求。
3. 出问题时的第一步就是「先改回去」，多一次点击就多一次犹豫。

**代价**：填到一半的文本不会保存（用 `change` 而不是 `input`，失焦才提交）。
这是有意的 —— 用 `input` 的话，数字会被依次存成 `1`、`10`、`100` 三个中间值，
中途关页面就留下一个错的配置。

**配套**：每个字段旁有「已改」标记，说明它和默认值不同。
出问题时先看这几项，比逐条对照文档快得多。

## D44 · 前端自检用假 DOM，不等浏览器

**决定**：`server/tools/check-web.test.mjs` 里手写一个最小 DOM（约 120 行），
把 `createSettings` 真跑一遍，用**真实 manifest** 渲染。

**为什么**：这台机器上的无头浏览器起不来（`--screenshot` 和 `--dump-dom`
都输出 0 字节，换过 headless=new/old、关闭沙箱、换 profile 目录）。
而"面板点开才白屏"是最难排查的一类问题：服务端一切正常，控制台一行红字。

**假 DOM 的边界**：它不证明"好看"，只证明**不抛异常、字段不漏、控件类型都有**。
所以它挡的是"点了就崩"，不是"样式不对"。样式仍然需要人看一眼。

**顺手抓到的问题**：假 DOM 第一版没有实现 `value` 属性（只有 `attrs.value`），
于是 `e.target.value` 是 `undefined`，测试显示"提交了空对象"。
这恰好说明这条测试是有意义的 —— 它真的在读表单事件，而不是在断言自己造的数据。

## D45 · 布局用"算"来守，不用截图

**决定**：`server/tools/check-layout.test.mjs` 直接读 `web/app.css` 与 `web/index.html`，
算出「某个视口宽度下内容排不排得开」，把结论变成断言。不拍照、不跑浏览器。

**为什么**：这台机器的 Edge 无头彻底不可用 —— 五种参数组合（两个版本的可执行文件、
`--headless=new` 与 `old`、干净环境变量、临时 ASCII 路径、`--remote-debugging-port`）
全部在 71–505ms 内以退出码 0 结束，**不出文件也不出一行日志**，等于根本没启动。
而"排歪了"这个问题恰恰只有看图才发现。

**换成算法的好处**：断言给出的是数字，不是感觉。
护栏上线当天就抓到一个真回归：第 5 张统计卡是我后加的，卡宽下限仍按 4 张时的 148px，
于是 **1025–1163px 的窗口会掉成「4 张 + 1 张孤儿」** —— 这段宽度正好是左右分屏和
小笔记本，而 1024 以下本该切堆叠布局，所以**只看手机永远发现不了**。
下限改成 120px 后门槛降到 1024，桌面区间恒为一行。

**顺带纠正了两个我自己算错的数**：写注释时我把 `--s6` 当成 32px（实际是 24px），
又把"门槛"算成 1172px。护栏算出来是 1164px。**人能算错，代码读一遍就不会。**

**边界**：它只覆盖"排不排得开"，不覆盖"好不好看"。颜色、对齐、间距是否舒服，
仍然需要人看。护栏的作用是把"会不会悄悄坏掉"和"好不好看"分开对待。

## D46 · 启停脚本：判断"在跑"要看身份，不看端口

**决定**：`/api/status` 增加 `app: 'yuyue3'` 与 `pid`。
脚本判断服务在不在，靠这两个字段，而不是 `netstat` 里端口有没有 LISTENING。

**为什么**：只看端口会有两种假象，都是静默失败：

1. 别的程序占了 8900 —— 脚本以为"已经在跑"，打印启动成功，其实什么都没有；
2. 停止时按端口找 PID —— 会把别人的进程杀掉。

**停止的路径**：优先 `data/run.pid`（服务监听成功后自己写的），按端口兜底。
理由是新版 Windows 已经移除 `wmic`，没法再按命令行找 `node` 进程；
而"按端口找"会漏掉"起来了但还没绑定端口"的那几秒 —— 正好是点停止最容易点中的时间。

**为什么停止要留暂停标记**：看门狗每 5 分钟巡检一次。如果停止不留痕迹，
5 分钟后它会把进程拉起来，用户看到的现象是"停不掉"，而不是"被重启了"。
标记文件 `logs\yuyue3.paused` 只在 `stop` 时写入，只在**手动** `start` 时删除；
巡检任务带 `auto` 参数，看到标记就跳过。**"被自动拉起"和"我要它跑"必须是两件事。**

**为什么日志只在启动时轮转**：Windows 上文件被进程占用时 `move` 会静默失败，
边跑边轮转看起来成功了，其实日志还在无限增长。启动那一刻服务还没起，改名才是可靠的。

## D47 · 日志只压不删，读取透明

**决定**：明文分片超过保留窗口（默认 30 天）就在启动时压成 `.jsonl.gz`，
原件删除；`readAll()` / `readAllAsync()` 遇到 `.gz` 自动解压，调用方无感。

**为什么不能删**：日志是唯一事实来源。删一天，就等于把那天的账本烧了 ——
战报对那天永远算不出来，而且没有任何痕迹说明"这里本来有数据"。

**为什么必须压**：一天 2MB 左右，一年几百 MB。不压就是慢性膨胀，
而 99% 的用途只是"翻一眼上周三"。

**三个安全点**：

1. 只动保留窗口之外的（按日期键比，含今天的永远不碰）
2. 压完立刻解压比对字节，不一致就删掉 `.gz` 保留原件
3. 归档后 `seq` 恢复要能续上 —— 全部归档时没有明文可读尾部，
   只能解压扫描。这条单独有断言，因为"返回 0 让整场统计冻结"是审计抓过的致命 bug

**代价**：`_shards()` 里多了 gz 分支，`scanMaxSeq` 也要认两种格式。
用"同一个日期键只会有一种文件"换来排序简单。

## D48 · 战报从日志重算，不读内存

**决定**：`/api/reports` 每次都 `readAllAsync()` 然后 `new Projection()` 重跑一遍，
不复用线上那个 Projection 实例。

**为什么**：线上实例只保留"当前场 + 已封存场次"，进程一重启 `sessions` 就空了。
复用它会出现"重启后战报变少"，而且是静默的 —— 用户只会觉得"昨天那场怎么没了"。

**代价**：每次打开战报要读全量日志。9,228 条实测 40ms 左右，可接受。
真要更快就得做增量索引，那是另一个复杂度，现在不值得。

**顺带修的 bug**：`_closeSession()` 原来不判 `closed`，于是 `LIVE_END` 关掉一场后，
下一次 `LIVE_START` 又用**新一场的开播时间**把上一场的 `endedAt` 覆盖掉 ——
"播了 4 分钟，战报显示 1 小时"。这个字段一直没人读，所以一直没暴露。
**只写不读的字段最容易烂。**

## D49 · 沙盒必须用独立的插件实例

**决定**：沙盒加载插件时给 import URL 加随机 query（`?sandbox=...`），强制一份新模块实例。

**为什么**：ESM 按 **URL** 缓存。同一个 `plugin.mjs` 第二次 `import` 拿到的是
同一个对象 —— 而 welcome 的冷却表、gift 的连击计数都挂在模块级。
不隔离的话，沙盒会拿**线上正在用的**冷却表去试跑：结果既不准，
还会反过来把正在播的那一场搅乱。

**怎么验**：连续跑两次同样的回放，配置 `cooldownSec: 600`。
若两次都说了一句 → 隔离生效；若第二次 0 条 → 共用实例，断言变红。
这条断言做过反向验证（去掉 cacheBust 立刻 FAIL）。

## D50 · 插件投递串行，队列满就丢并计数

**决定**：`PluginHost.deliver()` 把事件排进单消费者队列，按到达顺序依次处理；
`room-runner` 不再 fire-and-forget 调 `dispatch()`。

**为什么**：收包不能等插件（丢包比延迟糟），但**顺序不能靠运气**。
直接不 await 地调 `dispatch()`，两条事件会并发进同一个插件：
连击计数错位、冷却表读到中间态。这类 bug 不报错、不掉线，
只是"偶尔少答谢一次"——最难查的那种。

**队列上界 5000**：反压。某个插件卡住（SC 等闸门槽位最多 5 秒）时后面的全排队，
排到 5000 说明插件已经病态，这时丢新事件比无限吃内存好。
但**丢弃必须可见**：计数进快照，界面上能看到 `dropped`。

## D51 · 旧日志的金额偏差要主动说出来

**决定**：`/api/reports` 返回 `warnings`，检测到旧格式 SC（缺 `yuan` 字段）就提示
"有 N 条醒目留言由旧版本采集，金额会偏低"。

**为什么**：SC 金额曾经差 1000 倍、又差 10 倍，最终改成读报文自带的 `rate` 才对。
日志是 append-only 的，**错误的历史数据永远留在那里**，不会被改写 ——
这是对的（改写事实日志比留下错误更危险），但战报必须把这件事说出来。

**否则**：用户看到"2 条醒目留言，共 0.1 元"，只会得出一个结论：这软件算错了。
让他自己去发现"这数字明显不对"，等于没做。

## D52 · 场次时长只能"推断"，而且必须说出来是推断的

**决定**：
1. 场次记 `lastEventTs`（本场最后一条事件的时间）。
2. 没有 `LIVE_END` 的场次，结束时间取 `min(下一场开播/下一条 LIVE_END, lastEventTs + 60s)`，
   并打 `endedAtEstimated = true`；战报显示成「约 4 分钟」。
3. 机器人启动时补的那条 `LIVE_END` 带 `synthetic: true` —— 它不是 B站 说的，
   时间戳是"我启动的那一刻"。
4. 开着的场次若 30 分钟没有任何事件，标 `stale`，时长冻结在最后一条事件，
   前端显示「已中断」而不是「进行中」。

**为什么**：审计实测，断网 + 20 小时后重新开播，上一场被算成 **1200 分钟**。
原因是没有 LIVE_END 时只能拿"下一场开播时间"当自己的结束时间 ——
断网、进程被杀、B站 漏推都会走到这条路，数字错得离谱却**不报错**。

根本原因很典型：`endedAt` 从写进去那天起就**没有任何代码读它**。
实时统计只关心"现在这一场"，场次列表只是存着。战报第一次读时长，假数字立刻现形。
**只写不读的字段最容易烂** —— 这条要记住。

**为什么用 30 分钟**：真实日志里 `ONLINE_COUNT` 是采样推送，一场 1334 条、p99 间隔 8 秒。
"半小时一条事件都没有"不可能是还在进行的直播。取保守值是因为：
宁可把一场安静的长播算作进行中，也不要因为一时没人说话就把正在播的场次判死。

**代价**：如果一台机器**真的**断网 3 小时但直播还在继续，时长会少算 3 小时。
这比"多算 17 小时"好 —— 而且日志里本来就没有那 3 小时的数据，少算才是诚实的。

## D53 · 归档被打断时，按日期去重而不是按文件读

**决定**：`_shards()` 按日期键去重，同一天明文与 `.gz` 并存时**用明文**，
并在 `stats().duplicateDays` 里报出这些日期。

**为什么**：归档顺序是「写 .gz → 解压校验 → 删明文」。进程如果正好在
写完 .gz、还没删明文时被杀（断电、任务管理器结束进程），同一天就会两种文件并存。
按文件逐个读的话，这一天的事件会被读两遍 —— 实测 2 条读出 4 条。

**后果不是"统计翻倍"**（投影按 seq 幂等，会跳掉重复的），而是更阴的两种：
- `reconcile` 的独立求和路径会算成两倍 → **对账永远失败**。
  而对账失败一旦成为常态，真出问题时就没人在意了；
- 战报的"旧版 SC 金额偏低"警告条数翻倍。

选明文是因为它一定含 .gz 的全部内容（归档只动保留期之外的日期，之后不再写入），
而且它是还能被 append 的那份。

## D54 · 对账不许用展开运算符求 min/max

**决定**：`reconcile` 里用循环求 min/max，不用 `Math.min(...seqs)`。

**为什么**：展开会把整个数组变成实参。实测本机上限在 12 万～20 万条之间，
超过就 `RangeError: Maximum call stack size exceeded`。
日志是 append-only 的，一场 9000 条的话二十几场就摸到这条线 ——
这不是"也许有一天"，是"开播一个月必然"。

而且它报错的方式特别难归类：`/api/reconcile` 会变成"点了没反应"，
而不是"对账失败"，排查时会先怀疑前端。

**顺带修掉一个假阳性**：`序号连续` 这条原本是 `maxSeq - minSeq + 1`，
空日志时 min=max=0 会算出 1，于是"0 条日志"被判成"序号不连续" ——
新装第一次启动就报一次对账失败。对账失败本该是强信号，被假阳性磨没了就没人看了。

## D55 · 心跳发送要兜住，别让一次正常重连把进程带走

**决定**：`live-client` 的心跳 `ws.send()` 包 try/catch，失败就主动走重连。

**为什么**：`readyState` 检查与 `send` 之间没有异步间隙，但 socket 可能在
**同一轮事件循环里**已经被 close 置成 CLOSING，此时 `send` 会同步抛。
定时器回调里抛出的异常没人接，会被 `uncaughtException` 接住，
而 `main.mjs` 对未捕获异常的处理是**关掉整个进程**。

也就是"心跳撞上一次正常重连"会让机器人直接退出 —— 代价完全不成比例。
（进程崩掉还有看门狗能拉起来，但那意味着断流、重放、场次被切碎。）

## D56 · 弹幕截断按码位，不按 UTF-16 长度

**决定**：`prepareText` 超长时按 `Array.from` 的码位截断，
长度仍按码元判断（B站 数的是码元）。

**为什么**：`s.slice(0, 20)` 数的是 UTF-16 码元。B站 名字里的 emoji 占两个码元，
正好切在中间就会留下孤立代理项（lone surrogate），发出去是乱码方块。
只在"名字里有 emoji + 文案刚好卡在边界"时出现，几乎不可能复现 ——
所以只能靠断言钉住，不能靠试出来。


## D57 · 关键词回击默认「整句相等」，不默认「包含」

**决定**：`matchMode` 默认 `exact`。包含匹配可以做，但必须由用户主动选。

**为什么**：包含匹配听起来更"智能"，实际是灾难 —— 一个 2000 人的房间每秒十几条弹幕，
只要有一句里带「晚安」，它就回；而且会命中「还没晚安呢」「晚安晚安晚安」这类正常聊天。
观众三秒就看出这是机器人，而这正是二代被吐槽最多的行为。

**推论**：默认值必须是**最安全的那个**，不是功能最多的那个。
用户想要更激进的效果，他自己会去改；反过来，被默认值坑了的人不会去查设置。

**配套**：冷却做成**规则级**而不是全局级。全局冷却会让「打卡」和「晚安」互相挤占，
而用户说"这个词一分钟回一次"时，他想的一定是那一个词。
另外，一条弹幕同时命中两条规则、前一条在冷却时，要用后一条而不是整体放弃 ——
这种漏回不报错，表现是"偶尔某句话没反应"，最难查。

## D58 · 定时播报：短周期唤醒 + 累加，而不是睡满间隔

**决定**：定时器每 5 秒醒一次，累加"已经等了多久"，攒够 `intervalSec` 才开口。

**为什么**：如果直接 `setTimeout(间隔)`，用户把 600 秒改成 60 秒后，
还得把剩下的 590 秒睡完才生效 —— 他的判断只会是"没保存成功"。
而"改配置立刻生效"是这个项目从 P2.5 起就定下的规矩。

同样的道理让另外两种情况都变得自然：

- 关掉再打开：攒的时间早就够，下一次唤醒（≤5 秒）就开口，不用等一整个周期；
- 未开播时打开：一开播就开口，而不是"再等 10 分钟"。

**代价**：每小时 720 次空转。一个空函数的开销，可以忽略。

**另一条**：`priority` 固定 0，撞上限速就跳过这一轮。
定时播报没有任何时效性，为它排队只会挤掉礼物答谢这类真正有反馈价值的话。

## D59 · 沙盒回放要说清"什么回放不出来"

**决定**：`/api/sandbox` 返回 `note`，说明"按时间触发的发言（如定时播报）
与回放速度有关，不在结果里体现"。

**为什么**：事件驱动的插件在回放里完全可复现（事件序列就是全部输入），
但定时播报的输入是**现实时钟** —— 回放把一小时的日志压缩成几百毫秒跑完，
现实时钟几乎没动。不说明这一点，用户会拿"回放里播报没出现"当成配置没生效。

这是"回放"这个功能本身的边界，不是 bug。边界要说出来，不然它会被当成 bug。

## D60 · 跨事件的状态放 `ctx.scratch`，不放模块对象

**决定**：`PluginHost` 给每个「宿主 × 插件」发一块 `scratch` 对象，通过 `ctx.scratch` 暴露。
新写的插件（`reply`、`schedule`）已经把状态放进去。

**为什么**：ESM 按 URL 缓存 —— 同一个 `plugin.mjs` 在一个进程里**只有一份模块对象**。
插件写 `this._last = new Map()` 时，`this` 指的就是那个共享对象。
单房间时完全看不出来；一旦两个房间同时跑，两边的冷却表就是同一张 Map，
症状是"隔壁房间回过，这个房间就不回"—— 不报错、不报警，只能靠猜。

沙盒那边早就踩过一次同一个坑（D49 的 `cacheBust`），当时只解决了"沙盒 vs 生产"，
没解决"房间 vs 房间"。`scratch` 是同一个道理的第二半。

**欠账已清（本轮）**：`welcome` 的 `Greeter`、`gift` 的待发队列 / 定时器 / 分发上下文、
`blind` 的冷却表、`sc` 的本场计数，全部迁进 `ctx.scratch`。

其中 `gift` 最隐蔽：定时器回调里原先读的是 `this._ctx`，多宿主时它指向
"最后收包的那个房间"，A 房间的礼物答谢会发到 B 直播间去。改成闭包捕获
本宿主的 `scratch` 之后，队列和定时器都跟着宿主走。

`check-play` 里补了两条架构级断言：B 宿主启动不得清掉 A 的冷却表 / 待发连击。
把实现改回模块对象，这两条必然失败 —— 欠账不许再回来。Q4 的前置条件已解除。

## D61 · 长期观众簿：按天分片、只追加、只存三样

**决定**：欢迎不再只靠 90 秒内存冷却。新增 `server/core/roster.mjs`，
按 `data/roster/<roomId>/YYYY-MM-DD.jsonl` 只追加记录「这个人来过」；
每人每天最多一行，只存 uid、最后来访时间、当时的名字。
超期整片删除，默认保留 90 天（比 `returningDays` 默认 30 天宽三倍）。

**为什么**：真实样本（8 小时、4206 次进场、3806 个不同的人）里，
重复的 400 次全会被再欢迎一遍；而且老观众占比只会越来越高，
进程一重启连那 90 秒冷却也没了。这是慢性病，不治会越来越疼。

不做全量重写的 `roster.json`：十万人约 4MB，每 5 分钟写一次就是一天 1GB
写入量，而这个数据一天只增加几百条。和事件日志同构，一天几十 KB。

**分工**：记账在**内核**（事件入库时统一 `mark()`），不在插件里 ——
插件关掉一个月再打开，整个房间不会突然全变陌生人。`_visit` 是挂在内存
事件对象上的派生字段，`append()` 已经序列化完才挂，因此不进日志。
判断留给 `plugins/welcome`：新观众 / 欢迎回来 / 静默 / 和新观众一样，由配置决定。

**沙盒**：回放用 `persist: false` 的内存簿，绝不写真实 `data/roster` ——
把历史事件记进真实簿子等于伪造历史，回放一遍那天的人就都变成"来过"了。

**降级**：簿子读不出来时，所有人按新观众处理。宁可多欢迎一句，
也不要因为一个数据文件让整晚没声音、还不报错。

## D62 · 观众簿里三处「看起来对」的写法其实是错的

**决定**（三条，都配了反向验证：把实现改回旧写法，对应断言必须失败）：

1. **剪枝必须用同一把尺子。** 分片是按日期删的（`day < cutoffDay`），
   内存就也必须按 `dayKey(rec.ts) < cutoffDay` 剪。用 `rec.ts < cutoffTs`
   看着更精确，却会把 cutoffDay 当天早几个小时的人从内存删掉、而磁盘上他还在 ——
   重启前后待遇突然改变，且不报错。
2. **上限定的是内存，不只是写盘。** 到 `maxPeople` 时新人既不写盘也**不进 Map**。
   早先只跳过写盘却照样 `set()`，Map 会一路涨，保险丝形同虚设。
3. **「同一天」要看上次是否真的写进盘里。** 写盘失败后若按内存时间判同天，
   今天剩下的所有来访都不会再重试，重启后他永远变陌生人。
   所以记的是 `writtenDay`，只有 `recorded` 成功才更新。

**另外**：1Hz 状态推送走 `brief()`（人数 + 分片数 + 保留天数，O(1)），
不走 `stats()`（逐片 stat + 遍历整张表求最早 / 最晚来访）。
十万人 × 1Hz 的全表遍历是纯浪费，而侧栏只需要知道「认识多少人」。
名单是观众的个人信息，不下发到这条通道上。

## D63 · 主动 @ 点名：名字反查 uid，查不到就降级并说清楚（已移除）

> **2026-11-03 已整体移除。** 用户要的是"不用人点"的自动打招呼（D64），
> 手动入口多余：`core/callout.mjs`、`App.callout`、`POST /api/callout`、侧栏面板、
> `Roster.findByName`、`check-callout` 13 项自检全部删净，`check-web` 另加一条
> "侧栏不再有主动 @ 面板"的回归断言。以下保留作历史记录，描述的是**当时的实现**，
> 不是现状。

并说一句招呼。uid 从**观众簿**按昵称反查（D61 已经存了 uid + 名字），也可以手填。
业务逻辑放 `core/callout.mjs`，依赖 gate / roster / roomId 全部注入。

**为什么单独走接口、不做成插件**：欢迎插件是事件驱动的，等人进场才说；
主动打招呼没有事件可依赖，只能由人触发。插件的输入应该是事件流，
塞一个"手动触发"进去会把 D5 的仲裁模型弄脏。

**为什么用观众簿反查**：B站 的 `reply_mid` 必须要 uid，光有名字发不出可点的 @。
观众簿正好有 uid + 名字，直接复用 —— 不引第二个数据源、不调 B站 搜索接口、
不建反向索引（人点一下才查一次，十万人扫一遍几毫秒，比维护索引并处理改名一致性强）。

**三条不能省**（都钉在自检里）：

1. 结构化 @ 时文案里**不能再写 @名字**：B站 会自己挂一个可点的 @ 标签，
   写两遍就成了「@小明 你好呀 小明」。只有降级成纯文本时才把 `@名字` 拼进文案。
2. 查不到 uid 时降级纯文本 @，但**必须说明它不可点、没有通知**。
   不说明的话，用户会拿"没 @ 到"当 bug 报回来。
3. 长度自己先检查：`prepareText` 会静默截断，而纯文本降级的 `@名字 `
   会吃掉好几个字，招呼语很容易被砍成半句。超长直接报错让人改短。

**闸门**：一律走 `SendGate.say()`，`reason` / `source` 都是 `manual`，priority 保持 0
（不为了一句招呼去挤占礼物答谢的等待槽位）。限速、去重、演练、写 SENT 事件一个不少。
被拦下是**一次成功处理过的请求**，结果放在响应体的 `sent / blocked / dryRun / hint`，
**不能用 HTTP 4xx 表达** —— 前端的请求封装遇到 `ok:false` 会直接抛异常，
用户反而看不到"为什么没发"那句话。

## D64 · 主动打招呼是「服务自己挑人」，不是「人点一下」

**纠偏**：D63 做的是手动点名，方向错了。用户要的是**不用人点** —— 服务自己定时挑
一位观众 @ 过去。D63 当时暂留作手动补漏入口，2026-11-03 已按用户要求整体移除
（见 D63 注）；主线是独立插件 `plugins/autocall`。

**决定**：新增定时插件，`claims: {}`、`onEvent` 恒返回 false，完全不认领事件。
到点读 `ctx.roster.recent()` 取候选，拼一句招呼，`ctx.say()` 带 `reply` 发出去。
默认关闭，默认间隔 300 秒，硬下限 60 秒。

**为什么不用事件流攒候选**：若声明 claims 去"旁观" ENTER，就必须排在 welcome
前面才看得到（claims 按优先级分发，第一个返回 true 的截断），且必须永远返回 false。
这个顺序约束很脆：以后调一下 welcome 的优先级就静默失效，而且不报错。
观众簿由内核在事件入库时统一记账，插件只读，禁用 / 换房间 / 沙盒回放都不影响它。

**两个时间窗**（少一个都会出问题）：
- `withinSec`：只挑最近来过的。少了它就会 @ 一个早走了的人，像自言自语。
- `minAgeSec`：跳过刚进场那几十秒。少了它会在欢迎语之后连着第二条弹幕 @ 同一个人。

两者互不相交时候选恒为空、功能"开了没反应"且无报错 —— 所以 `resolveWindow()`
自动夹到窗口一半并 warn 一次，不让配置静默失效。

**三条与 D63 同源、但在这里更容易踩的规矩**：

1. 文案里不写 `@名字`（结构化 @ 由 B站 自己挂标签）；超长直接跳过这一轮，
   不发被 `prepareText` 砍掉一半的话 —— 自动流程里没人能立刻改文案，只能记 warn。
2. 被限速 / 去重拦下**不算点过名**。若照旧标记 `called`，这一轮就白白消耗一个
   候选，表现是「偶尔一整轮谁也没被 @ 到」，且不报错。节奏照常清零（跳过这一轮），
   下一个间隔仍挑他。
3. 计时器、文案游标、每人冷却表全放 `ctx.scratch`（D60）。多房间串味的症状是
   "时有时无"，不报错。

**沙盒**：`startAll()` 会启动定时器，但插件默认配置关闭、且 `unref()`，
回放几百毫秒跑完就 `stopAll()`，不会真发。回放 note 把「主动打招呼」和
「定时播报」并列为按时间触发、结果里不体现的发言。

**验收**：`check-autocall` 24 项（假时钟，不等真实 300 秒；含一条真实 `PluginHost`
加载集成，验证 `ctx.roster` getter、`ctx.say` 包装与配置下发），四条反向验证逐条单独跑过：
去掉"不写重复 @"、去掉结构化 reply、改成"拦下也标记"、禁用定时器，
分别让 2 / 6 / 1 / 8 项变红，随后恢复源码。

## D65 · 招呼文案做成「前后端同一份」预设库（P4.9）

**诉求**：主动打招呼要内置几套有趣的文案，出厂就能选，不用主播自己编词。

**结论**：新建 `web/core/greetings.js`，5 套文案包。设置页直接 `import` 它
（静态服务本来就发 `.js`），Node 自检也能 import 同一份 URL（根 `package.json`
是 `type: module`）。纯数据、不碰 `document/window`，所以两边读到的是同一个模块
实例；manifest 的 `templates` 默认值由自检逐句比对，改了文案包忘了改 manifest
会立刻变红。

**2026-11-03 修订**：手动点名（D63）移除后，"单句下拉 / preset 解析"这条支线
一并删掉。现在预设只服务自动打招呼：设置页选一套 → 把整包 `lines` 写进
`plugins.autocall.templates` 配置，插件运行时只看配置、不认识预设 id，
因此也不需要后端接口或服务端解析。

| 决策 | 为什么 |
|---|---|
| 真源放 `web/core` 而不是 `server/core` | 前端要能直接 import。放服务端就得加 `/api/greetings` 再异步拉，多一条链路和一个失败点 |
| manifest 用 `presets: "greetings"` 标记 | 保持"前端不认识任何具体插件"：设置页的 lines 控件看到标记才渲染下拉，加新插件仍是前端零改动 |
| 选预设 = 立刻写进 `templates` 并保存 | 走和普通编辑完全相同的 `saveField` 路径（回填服务端值、失败退回），不做第二套配置写入逻辑。代价是会把默认值固化，但那是用户主动选的，符合预期 |

**文案三条硬规矩**（自检盯着）：

1. 不写 `@名字`：B站 收到 `reply_mid` 会挂可点的粉色 @ 标签，写两遍就成了
   「@小明 你好呀 小明」。
2. 不带 `{用户}`：预设是给"自动挑人"用的，昵称长度不可控，一个 30 字昵称就能
   把整句顶过 20 字上限被 `prepareText` 静默截断。不写名字，长度就固定可断言；
   自定义文案仍可用 `{用户}`。
3. 按码位 ≤ 20 字且尽量短：预设全部控制在 10 字以内，给自定义文案和长昵称留余量。

`matchPack()` 只认完全一致（顺序、句数都算），改过一句就是「自定义」，
设置页据此显示"当前预设"，避免选了却以为没生效。

**验收（移除手动点名后）**：`check-greetings` 8 项，`check-web` 补 1 条
「侧栏不再有主动 @ 面板、其他面板还在」的回归断言，全库 **365 项全绿**。
三条反向验证逐条单独跑过：把一句改超长（4 项红）、改掉 manifest 的 `presets`
标记（1 项红）、让设置页不渲染预设下拉（1 项红），随后恢复源码。

## D66 · 访问口令：挡的是「本机其它程序」，不是外网（P5）

**诉求**：观测台开在 `127.0.0.1:8900`，为什么要口令？

**结论**：因为只绑本地挡不住浏览器。任何一个你打开的网页都能向本机端口发 POST，
服务只检查 `Host` 头（防 DNS 重绑定），**不检查"谁让你发的"** ——
演练模式没关的话，一个恶意页面理论上能关演练、改文案、切房间。CSRF 就是这个形状。

所以是两道防线，口令只是第二道：

| 防线 | 位置 | 默认 | 挡谁 |
|---|---|---|---|
| Origin 检查 | `http/server.mjs` / `write-guard.mjs` | **开** | 跨站请求（一定带 Origin，对不上就 403） |
| 访问口令 | `core/access.mjs` | 关 | 本机其它程序、浏览器之外的 localhost 调用者 |

几条具体选择：

- **自定义头 `X-Access-Token`，不用 Cookie。** Cookie 浏览器会自动带、跨站也带，
  等于没防 CSRF；自定义头必须 JS 显式设置，跨域会先发预检，预检过不去就发不出去。
  一条措施同时解决"验证身份"和"挡住跨站"。
- **存 scrypt 加盐哈希，不存明文。** `data/` 经常被整个复制走（备份、换机器、发给别人看日志），
  存明文等于把口令一起送出去。`N=16384` 约 50ms：人点一下无感，暴力破解每秒 20 次封顶。
  明文永不落盘，也不出现在任何响应里（`status()` 只给 `enabled / updatedAt / minLength`）。
- **关掉是删文件，不是写 `enabled:false`。** 留一份用不到的哈希，只会在下次出问题时
  让人怀疑"是不是它导致的"。
- **`access.json` 读坏了就退化成"没设过"。** 宁可"口令没生效"，也不能"谁都进不来"。
- **连错 5 次退避 30 秒。** 只挡在线猜，不锁死用户；退避后重置计数，否则等完 30 秒
  试一次又被锁，会以为坏了。

**验收**：`check-p5` 35 项，含「磁盘上只有盐和哈希，没有明文」「对外状态里没有盐和哈希」。

## D67 · 自动更新只提示、诊断包白名单脱敏（P5）

**自动更新**（`core/update.mjs`）：半夜自动装失败 → 第二天开播发现机器人起不来，
而你不知道为什么。这个项目的每一处设计都在避免"静默坏掉"，所以**只检查、只提示**，
装不装由人决定。另外：

- 默认 `updateUrl` 为空。三代没发布到 npm、也没有固定 Release，编一个写死的地址
  等于让它永远 404，用户只会看到"检查失败"这种没信息量的提示。空的时候明确返回
  「尚未配置更新源」，不假装检查过了。
- 失败不抛异常，统一返回 `{ok:false, error:'人话'}`：这个接口失败概率远高于成功
  （没网、源挂了、格式不对），而"检查更新失败"不是错误，是**没有结果**。
- 版本比较只比数字段：`1.10.0 > 1.9.0`（字符串比较会得出相反结论，最常见的坑）。

**诊断包**（`core/diagnostic.mjs`）：这个包**是要发给别人的**（贴群里、发给你找人帮看），
而 `data/` 里最不能外传的是 `auth.json`（Cookie）和 `access.json`（口令哈希）。
所以构造方式是**白名单** —— 只挑明确字段写进去，而不是"复制一份再删几个"：
前者漏字段的结果是"信息不够"，后者只要漏一个就泄密，方向选错代价不对等。

| 内容 | 处理 |
|---|---|
| Cookie / 口令 | 一个字节都不进包，连摘要都不给 |
| 观众昵称 / 弹幕正文 | 不进包（第三方个人信息） |
| 观众 uid | sha256 前 8 位：仍能看出"是不是同一个人"，无法反查 |
| 自己的账号 | uid 保留，昵称打码成首字 + `***` |

ZIP 手写（store 模式，不压缩）：零依赖是硬约束（唯一外部依赖是 `ws`），
几百 KB 文本用不上 deflate，省掉一个压缩实现和解压依赖。

**验收**：`check-p5` 35 项，含「包里的 Cookie / 口令 / 密钥一律变成 `***`，值本身不出现」
与「事件骨架里没有昵称、没有弹幕正文」。

## D68 · 弹幕指令只认「整条消息恰好是一个词」，且优先级高于关键词回击（P4.10）

**诉求**：观众想知道"我上次什么时候来的""这场多少弹幕"，不该由主播手工回。

**结论**：新增 `plugins/command`，认 `#帮助` / `#本场` / `#我来过`。

| 决策 | 为什么 |
|---|---|
| 触发规则 = `^[#＃]\s*(\S{1,12})$`，整条消息 | 观众正常聊天带井号是常态（话题、编号、颜文字）。只要允许"包含"，`刚才那个#帮助有点用` 就会被回一句，热闹的房间里直接变成刷屏。宁可漏触发，也不能乱插话 |
| 全角 `＃` 也认 | 中文输入法打出来就是全角，不认等于半个功能没做 |
| 指令词上限 12 字 | 超长就不像指令而是句子了。`\S` 顺带保证中间没有空格 |
| `claims.DANMAKU = 120`（reply 是 100） | 否则用户配了一条 `帮助` 关键词，`#帮助` 会先被回击插件吃掉，指令永远到不了 |
| 非指令弹幕返回 `false` | 只是在"抢答"，不挡路。有一条真实 `PluginHost` 集成断言：`#帮助` 归 command 且 reply 的 `stats.claimed` 仍为 0，`打卡` 归 reply |
| 冷却期内**认领但不说** | 认领是"我看过了"。返回 false 会让这条弹幕漏给关键词回击再回一遍 |
| 记冷却在请求发送**之前** | 被闸门限速拦下也不该下一秒立刻再试，那只会让限速持续满格 |
| 只读，不写任何状态 | 这是**观众能触发**的功能。`#本场` 读投影、`#我来过` 只 `peek`，不改统计、不往观众簿写东西（有断言：查一次来访后 `roster.size` 不变） |
| 文案超 20 字照样发但要 warn | 否则用户只看到"回复少了一半"，不知道是自己文案太长 |
| 默认开启 | 三条指令本身无害且自带说明，出厂就该能用 |

**验收**：`check-command` 19 项，全库 **426 项全绿**。含一条反向验证：
把解析换成"包含即触发"的等价实现，`刚才那个#帮助有点用` 立刻被当成指令 ——
证明"整条消息"这条规则不是摆设。

## D69 · 观众簿要记住「这一次之前的那一次」（`previousSeenAt`）

**问题**：`#我来过` 上线时用的是 `peek(uid).lastSeenAt`，结果对**任何在场的人**
都回答"今天"。原因很直白：观众一进房间，内核在事件入库时就 `mark()` 过了，
`ts` 已经是"现在"——问"你上次什么时候来的"，答案永远是刚才。

**结论**：`_seen` 的每条记录多存一个 `previousSeenAt`（这次之前的那一次），
`peek()` 一并返回。

| 决策 | 为什么 |
|---|---|
| 在 `mark()` 里顺手记 | "上一次"这个值只在那一个瞬间存在，之后不会被任何地方重新算出来 |
| `load()` 从相邻分片取同一个口径 | 否则重启一次，所有人的"上次"都变回"从没来过"，`#我来过` 会对老观众说"第一次见你呀" |
| 不新增接口 | `mark()` 本来就在返回 `previousSeenAt`（欢迎插件用它判断"新观众 / 欢迎回来"），这里只是把它存下来，口径完全一致 |
| 插件侧仍要挡 `prev <= 0` | `agoText(0)` 会算出"两万天前"。没有记录就按第一次见处理，不替调用方编答案 |

**取舍**：同一个进程里同一个人反复进场，`previousSeenAt` 会被刷成"今天早些时候"。
这是**诚实的**（你上一次确实是今天来的），而且观众簿刻意不记弹幕与点赞
（见 `ROSTER_EVENTS` 注释），所以刷新的频率远低于想象。

**验收**：`check-command` 里两条断言直接钉住口径 —— 三天前来过、今天又进来的人，
`#我来过` 必须说"3 天前"；真实宿主 + 真实观众簿再验一遍跨天的那一次。

## D70 · 战报趋势图：手写 SVG、按天聚合、不做双轴（P4.11）

**诉求**：战报只有数字看不出趋势 —— 哪天人多、哪天收入高，得靠一行行读卡片。

**结论**：服务端 `buildDailySeries()` 按天聚合，前端 `svgEl()` 画柱状图。

| 决策 | 为什么 |
|---|---|
| 从**战报摘要**聚合，不从原始事件重算 | 从事件算就要再写一遍"礼物多少电池、舰长怎么折、SC 的元怎么变电池"—— 那是第二个真相，迟早和 `Projection` 分叉（二代就分叉过，差 1000 倍）。这里只做加法 |
| 空一天补一个全零的桶 | 不补的话两根柱子挨着，看起来像"连着播了 N 天"。趋势图最不该骗人的就是这一点 |
| 只在首尾之间补，不补到"今天" | 范围两头是"最近 7 天"这种**查询参数**的事，服务端不该假装知道；那部分由卡片上的汇总交代 |
| 一次只画一个指标，可切换，不做双轴 | 弹幕几千条、收入几十块，双轴的比例怎么取都会误导。切换不重新请求：序列只有一份，换的是画法 |
| 切指标后**不重新请求** | 同上。有断言盯着 `calls` 计数没变 |
| 值为 0 的那天不画柱子 | 画一根 0 高的线看不出来，反而让"没播"和"播了没人说话"在图上长得一样 |
| 柱子宽度封顶 56 并居中 | 只有两三天时柱子会被拉成一整块色斑 |
| 按**开播那天**归日 | 22 点播到 2 点的那场，四个小时都算前一天。比"按小时切、切出来的两半跟哪一场都对不上"清楚，图下面把这句写出来 |

**顺手记一个"看不见的失败"**：SVG 必须用 `document.createElementNS` 造。
用 `createElement('rect')` 得到的是 `HTMLUnknownElement`，塞进 `<svg>` 里会被整棵丢掉 ——
页面一片空白，控制台**一句话都没有**。所以 `dom.js` 里单开了 `svgEl()`，
且 SVG 元素的 class 走 `setAttribute`（`className` 在 SVG 上是只读的 `SVGAnimatedString`，
严格模式下直接赋值会抛）。自检里有一条断言 `namespaceURI === 'http://www.w3.org/2000/svg'`。

**验收**：`check-report` 3 项（同日多场合并 / 空天补 0 / 上限与脏数据）+
`check-web` 1 项（真 SVG、柱子数、切换指标不重新请求），全库 **430 项全绿**。

## D71 · 时间轴回看：格子是累积量，喂投影必须按 seq（Q5）

**诉求**：战报回答"这一场总共怎么样"，但看不出"怎么走过来的" ——
第 20 分钟弹幕为什么突然涨、收入是哪一刻起来的、机器人当时说了什么。

**结论**：`buildTimeline()` 把一场按时间切成格子（默认 60 秒），每格给一份**累积**快照；
前端一根滑块拖着看，柱子是"这格新增了多少"，顶部细线是值得回看的事件。

| 决策 | 为什么 |
|---|---|
| 窗口是**一场**（startedAt → endedAt），不是"一天" | 22 点播到 2 点那一场按天切会被劈成两半，前半段和后半段各自都读不出"这一场" |
| 格子给**累积量**，不给增量 | 累积量能和战报对账：最后一格必须等于战报卡片。增量少一条事件就永远差一点，且查不出来 |
| "这格新增"由服务端算好（`danmakuDelta`） | 前端拿相邻两格相减，等于把"累积量"的定义再写一遍；哪天定义变了图会静默变成二阶差分 |
| 喂投影**按 seq**，不按时间 | `Projection.apply()` 幂等去重（`seq <= lastSeq` 直接丢）。按时间排过一次，结果一条迟到事件凭空消失、总计少 1 —— 这种错误不报错，只是数字不对 |
| 格子按时间切、事件按 seq 喂 | 两者不一致（时钟被校准过）时以 seq 为准，语义等于线上"迟到的事件算在它到达之后"。合计不受影响 |
| 标记里**没有弹幕** | 八小时一万多条，全带上就是几 MB；观感上也会把真正的礼物/SC 冲走。弹幕的量由柱子表达 |
| 标记含 `SENT` | "机器人当时说了什么"是这个工具最需要回看的东西 |
| 格数上限 2000，**自动加宽**格子 | 40 小时按 10 秒切是一万四千格。截断会让时间轴停在半路 —— 而回看常常就是为了看结尾 |
| 空窗口返回空 `frames`，不是一排 0 | 一排 0 看起来像"这一场没人说话"，实际是"这一段没有日志" |
| 按一场而不是整天取窗口 | 与沙盒（按天）不同没关系：两者回答的问题不同，硬凑一个参数只会让两边都别扭 |

**顺带记一个坑**：`Projection` 的幂等是按 `seq` 的，所以任何"重放事件"的地方
（时间轴、沙盒、对账）都必须按 seq 顺序喂。时间轴天然想按时间排，正好踩在这上面。

**接口层的坑**：`Number(url.searchParams.get('from'))` 在参数缺失时拿到 `Number(null)`，
也就是 **0** —— 于是 `?to=...`（忘了 from）能一路通过"to > from"的校验，
最后报出"时间轴最长支持 7 天"这种和真实原因无关的错误。参数一律先判"有没有传、是不是空串"，
再转数字（同类的还有口令校验：`trim()` 之后才比较，否则带空格的口令设得进、解不开）。

**验收**：`check-timeline` 16 项（分格 / 边界归属 / 乱序输入等价 / 与战报逐字段相等 /
空窗口 / 格宽收敛 / 标记筛选与截断 / 接口参数校验 6 项：形状一致、缺参报错、7 天边界、
格宽收敛、未启动 503、并发 429）+ `check-web` 1 项（点开 → 请求窗口正确 →
拖动时读数与标记跟着走 → 返回列表），全库 **471 项全绿**。

## D72 · 有时间含义的判断一律用事件时间（顺手修掉三处）

**问题**：冷却读的是 `Date.now()`，而沙盒回放把四小时日志压成几百毫秒。
于是一个人四小时里问两次 `#本场`，回放里只答一次 —— 而当时是答了两次的。
回放少说几句不会报错，用户只会觉得"我改了配置怎么没反应"。

**结论**：凡是"过了多久"的判断，基准都用 `ev.ts`；只有**定时器**（定时播报、
主动打招呼）本来就看现实时钟，回放里不体现 —— 这一点写在沙盒返回的 `note` 里。

同一轮还修了两处同类的：

| 位置 | 问题 | 修法 |
|---|---|---|
| `plugins/reply` / `command` / `welcome` | 冷却读 `Date.now()`，回放里时间被压缩 | 传事件时间；`ts` 缺失或为 0 时退回真实时钟 |
| `core/sandbox` | `ctx.state` 是常量 `{roomId}`，`#本场` 在回放里永远说"0 条弹幕，0 位观众" | 回放自己维护一个 `Projection`，逐条先投影再投递（与线上顺序一致） |
| `core/access` | 设置口令时 `trim()` 了，校验时没有 —— 带首尾空格的口令设得进、解不开 | 校验也 `trim()`，口径只在一处定义 |

**验收**：`check-play` / `check-plugin` / `check-command` / `check-report` 各加一条时间基准断言；
`check-p5` 加一条"带空格的口令也认"。

## D73 · 时间轴的柱子按时间画（不是按槽位），跨天要写日期

**问题**（时间轴上线后回看时发现，两处都不报错）：

| 现象 | 根因 | 后果 |
|---|---|---|
| 播了二十小时以上的场次，右半边一根柱子都没有 | 柱子按"第 i 格占第 i 个槽位"等宽摆，且每根有 0.6px 下限；格数超过约 1120 时 `0.6 × 格数` 超过画布宽 | 溢出部分被 SVG 裁掉。轴上写着"播到 00:00"，图上什么都没有 —— 越长的场次越明显，而长场次恰恰最需要回看 |
| 光标压在前一根柱子上，读数却是这一格的 | 柱子等宽、光标按时间比例，两者只在"窗口正好是格宽整数倍"时才对得上 | 拖到后面越偏越多（实测 31 格错 10px）。读数看着像"这一格"的，其实是隔壁的 |

**结论**：柱子、刻度、光标统一走同一个 `xAt(ts)`（时间 → 像素）。

- 柱子的左右边界就是"这一格的起止时刻"，所以柱子总宽恒等于画布宽，**不可能溢出**；
- 最后一格不满时自然变窄 —— 这是事实，不是缺陷；
- 刻度一定落在对应柱子的右边界上，光标也一样。

同时修掉标题：`11-02 22:00 → 02:00` 看起来像同一天凌晨，而那是**第二天**。
跨天时结束时间也带日期。

**验收**：`check-web` 加 3 项（1200 格的柱子不出画布 / 每格柱子对齐光标时刻 / 跨天标题带日期），
三条都在旧实现下验证过会红。

## D74 · PWA：只缓存壳，不缓存数据（Q1）

**诉求**：战报、时间轴要在手机上看。加到桌面之后像 App 一样打开，不用每次找地址。

**结论**：`manifest.webmanifest` + `web/sw.js`。

| 决策 | 为什么 |
|---|---|
| **`/api/` 与 `/ws` 一律不接管** | 一个看统计的工具，最坏的情况不是打不开，而是**打开了、数字却是昨天的** —— 打不开人知道断了，旧数字会被当成真的 |
| **网络优先**，失败才回落缓存 | 零构建没有内容哈希，缓存优先等于"改完代码要记得手动升版本"，迟早出现"我明明改了页面还是旧的"。本地网络延迟几乎为零，这个代价可以忽略 |
| 安装时**自己爬**依赖 | 没有打包器给出资源清单；手写清单加一个 `views/xxx.js` 就漏一次。顺 `import` 与 HTML 的 `src/href` 走一遍，漏不掉 |
| 爬取认得粗（注释里的示例也抓） | 抓到不存在的路径就是一次 404 后跳过；为了排除注释去写 JS 词法分析器，不值得 |
| **单文件失败不影响安装**（allSettled 语义） | 某个图标 404 不该让整个离线能力装不上 |
| 只有导航请求回落成 `index.html` | 拿 HTML 顶替 JS，浏览器会把它当脚本解析，报一堆莫名其妙的错 |
| 断网时**明说** | SW 装好后断网打开，壳和布局一样不少，只有数字停住 —— 不提示会让人以为"直播间真的没人说话" |
| `type: 'module'` 注册 SW | 这样"哪些请求该接管、离线回落到哪"能抽成 `web/core/sw-policy.js` 的纯函数，进自检；否则这些判断只能靠人工在浏览器里点 |
| 图标用脚本生成 PNG | 4 个图标不值得引 sharp/canvas（几十 MB 原生依赖）。PNG 的最小可用子集不到 60 行，`npm run icons` 随时重出 |

**验收**：`check-pwa` 15 项 —— 清单字段、图标真的是声明尺寸的 PNG、
`.webmanifest` 的 MIME（发成 `application/json` 浏览器就不给装）、
真起服务把整个壳取一遍（漏一个文件就红）、接口/WS/跨域/POST 都不接管、
预缓存覆盖 `web` 下每个源码文件、断网提示开关、注册失败不炸主流程，
最后**用假的 `self`/`caches` 把 `sw.js` 真跑一遍**（install 真的抓完整壳 →
activate 真的删旧缓存 → 断网时导航真的回落成壳）。

最后这条是必要的：SW 最容易错的不是逻辑而是接线（事件名写错、`respondWith` 没调、
`skipWaiting` 漏了）。这类错误源码断言全都"看着对"，装进浏览器却完全没反应，
页面上一个报错都没有。

**三条反向验证**：把 `/core/sw-policy.js` 从预缓存起点删掉、让 `/api/` 不再被跳过、
去掉 `.webmanifest` 的 MIME —— 对应三条断言分别变红，其余不动。
另外把 `sw.js` 的 `shouldHandle` 判断和 `skipWaiting()` 各删一处，集成断言立刻红。

## D75 · 多房间：切换是换视图，不是搬家（Q4）

**诉求**：一台机器同时盯几个直播间，切过去看的时候别丢东西。

**结论**：App 层持有 `rooms: Map<输入号, {runner, events, oldestSeq}>`，
`runner` 只是"当前在看的那个"。

| 决策 | 为什么 |
|---|---|
| **切换不停旧房间** | 停掉再起的话，回来时那一场中间断了一段，统计要靠重放补齐，B站 长连也得重建 —— 每次切换等几秒，多房间就没意义了 |
| **缓冲挂在房间上，不挂在 App 上** | 挂在 App 上就得"切的时候清空 / 重读日志"。清空会丢后台房间的事件，重读日志是同步 IO，切一次卡一下 |
| **`_onEvent(room, rec)` 显式带房间** | 读 `this.runner` 的话，后台房间的事件会被记进当前房间 —— 两个直播间的数字搅在一起，页面上**看不出任何异常**。反向验证里把这一行改回 `this.runner`，两条断言立刻红 |
| **只把当前房间的事件推给页面** | 页面只有一个视图。后台房间的状态走 `/api/rooms` 看汇总，不挤在同一条 WS 上 |
| **按"输入号"做键，但真实号也认** | 短号要联网解析才知道真实号，而用户下次还会打同一串数字；两个号都认，才不会把同一个直播间开成两份（长连翻倍、日志写两个目录、统计变成两半） |
| 上限 **10 间** | 每间一条长连 + 一个插件宿主 + 一份投影。10 间在普通机器上是几 MB 内存；再多就不是一台机器该干的事了 |
| **必须留一间** | 全关掉之后页面没有数据源，"打开房间"的入口也没地方点 —— 那不是省资源，是自己把自己关在门外 |
| 插件配置**不分房间** | 文案属于主播的人设，换个直播间不该变成另一套话（Q7）。真要分开时按 `pluginConfigs[roomId]` 叠加 |
| 房间列表**随状态一起下发** | 每次 `status()` 现算：房间数最多 10 个，而"哪间在播、多少弹幕"随时在变，缓存只会显示过期状态 |

**顺带修掉**：`server/http/server.mjs` 的兜底错误处理把 `err.code` 抹成了 `bad_request`，
于是 App 层特意分的 `last_room` / `too_many_rooms` / `bad_room` 全被吞掉 ——
页面只能靠人话分辨"这是最后一间不能关"和"参数没传"，而人话是会改的。

**验收**：`check-rooms` 15 项 —— 房间号归一化、启动按配置起多间并激活记住的那间、
切已有的不重建不断流、切新的旧的不停、短号/真实号不重复开、上限拒绝、
事件按房间隔离（后台房间不进当前缓冲、切回来还在）、重复 seq 不记两次、
关闭只停一个 / 关当前自动切走 / 最后一间拒绝、配置落盘、
`GET /api/rooms` 形状、`POST /api/rooms/close` 缺参 400。

**三条反向验证**：把 `_onEvent` 改成读当前房间、`_findRoom` 不认真实号、
切换时顺手停掉所有房间 —— 对应的四条断言分别变红。

## D76 · 回放里"稍后再说"的话必须结清

**问题**：默认配置下，沙盒回放**一条礼物答谢都没有**。

三处叠在一起：

1. 礼物答谢开了连击合并（默认 8 秒窗口），答谢要等窗口结束才发，靠一个 200ms 的定时器；
2. 回放把三小时日志压进几十毫秒，定时器一次都不会到点；
3. `onStop` 把没发出去的待发队列**直接丢掉**（这是线上刻意的：重启后重放会变成重复答谢）。

于是用户改了答谢文案 → 去沙盒看效果 → 一片空白 → 以为配置没生效。

**结论**：

| 改动 | 为什么 |
|---|---|
| 合并窗口改用**事件时间**，并在每条礼物事件进来时先结算到期的 | 线上事件时间≈现实时间，行为不变；回放里"40 秒后的礼物"才不会被当成同一毫秒 |
| 新增 `onReplayEnd`（**只有沙盒会调**），把攒下的一次性结清 | 最后一条答谢后面没有事件来触发结算，不结清就是"结尾那句凭空消失" |
| `blind` 的冷却也改用事件时间 | 和 D72 同一类：回放里同一个人四小时开两个盲盒只会播一次，而当时是播了两次的 |

**顺手修的**：战报每日趋势图的柱子有 1px 宽度下限 + 1px 缝隙，天数超过约 330 天时
`天数 × 2px` 超过画布宽，**最近那些天被 SVG 裁在画布外面** —— 图上写着"365 天"，
右边却什么都没有。和 D73 的时间轴是同一个病根（下限不能把总量顶出画布），
修法也一样：先保证 `柱宽 + 缝 <= 槽宽`。

**验收**：`check-gift` 4 项（合并按事件时间 / 窗口内仍然合并 / 收尾结清 / 盲盒冷却按事件时间）、
`check-report` 1 项（默认配置下三条礼物三条答谢，最后一条也不许丢）、
`check-web` 1 项（365 天时最右一根柱子不能越界）。
反向验证：把事件时间改回 `Date.now()`、去掉 `replayEnd` 调用、把柱宽改回旧公式 ——
对应断言各自变红，其余不动。全库 **527 项全绿**。

## D77 · 插件配置和演练开关是「整台机器」的，不是「当前那间」的

**问题**：多房间上线后，改插件配置、开关插件、切演练模式，**只有页面正在看的
那一间生效**。后台那几间的宿主/闸门还停在旧状态。

三个现象，全都不报错：

| 操作 | 表面现象 | 实际后果 |
|---|---|---|
| 改欢迎语 | 当前房间立刻变 | 切到别的房间是旧文案，切回来又对了 —— 像随机故障 |
| 停用插件 | 当前房间停了 | 后台房间照旧说话 |
| **切到演练模式** | 顶栏显示已静音 | **后台房间还在真发弹幕** —— 用户以为不会说话，其实一直在说 |

**根因**：配置存在 App 上（D75 的决定：文案属于主播人设，不分房间），
但真正读它的是每个房间**各自**的 `PluginHost` / `SendGate` ——
每个宿主启动时把配置 `coerce` 了一份自己的副本。写路径只改了
`this.runner` 那一份。

**结论**：写路径全部改成「改完当前那间，再同步到其它房间」。

| 决策 | 为什么 |
|---|---|
| 新增 `_syncHosts(exceptHost, fn)` | 一处实现，四个调用点（改配置 / 恢复默认 / 启停 / 以后新增的都走这里） |
| `setDryRun` 直接遍历 `rooms` 改所有 `gate` + `runner.dryRun` | 这个开关回答的是"这台机器今天允不允许说话"，和"页面在看哪一间"无关 |
| 单个宿主同步失败只 `warn`，不抛出 | 已经有一间成功了；为了一间失败把整次请求回滚，用户会看到"改失败但值变了"，更混乱 |
| 新开房间仍从 `this.pluginConfigs` 起 | 这条本来就是对的，补一条断言锁住（回归时最容易连带弄坏） |

**连带修掉**：换房间时如果插件面板开着，面板不刷新。
配置是全局的（切房间不变），但**认领 / 发言 / 报错这些计数是分房间的** ——
不重拉就会一直显示上一间的数字，看起来像"新房间也说了这么多"。
`reset` 分支现在会 `settings.reload()`。

**验收**：`check-rooms` 6 项新增（改配置同步到所有宿主、在后台房间改也会回来、
启停对所有房间生效、恢复默认、演练开关对所有闸门生效、新房间带最新配置）、
`check-layout` 1 项（`reset` 分支必须重拉面板）。

**反向验证**：把 `_syncHosts` 的三处调用删掉、`setDryRun` 改回只改 `this.runner` ——
5 条断言立刻变红；把 `settings.reload()` 从 `reset` 分支删掉 —— 面板那条变红。

## D78 · 四处"看起来没问题"

都是"数字/文件名看着正常，其实是错的"，共同点是**不会让任何东西报错**。

| # | 位置 | 错在哪 | 后果 |
|---|---|---|---|
| 1 | `core/sandbox.mjs` | 回放的观众簿只认 `ENTER`，线上按 `ROSTER_EVENTS` 认 6 类 | "只送了礼、没触发进场报文"的人在回放里是陌生人，欢迎语少一句"欢迎回来" —— 而回放存在的全部意义就是"结果等于当时会说什么" |
| 2 | `core/projection.mjs` | `this.sessions.map(summarizeSession)` —— `map` 把**下标**当第二个参数传进去，而它是 `now` | 已封存场次有 `endedAt` 兜着，看不出问题；一旦某场 `endedAt` 为 0（旧数据、手工修过的日志、以后新增的封存路径），时长变成 `max(0, (0 - startedAt)/1000) = 0`：三小时的直播显示 0 分钟 |
| 3 | `core/diagnostic.mjs` | 诊断包文件名用 `toISOString()`（UTC） | 本地 12:55 的包叫 `04-55-40`，而日志分片是本地日期、日志行是本地时间。用户拿着"04 点"的包说"我 12 点出的问题"，对不上 |
| 4 | `web/views/reports.js` | `load()` 没有请求序号，也没有处理 429 `busy` | 连点范围（7 天 → 30 天）时先发的后到，**旧结果顶掉新结果**：chip 高亮 30 天、图上还是 7 天；撞上"上一次还在算"则直接把这句话当错误甩给用户，等于让他再点一次 |

**结论**：

1. `ROSTER_EVENTS` 从 `room-runner.mjs` 搬到 `core/events.mjs`（线上入库和沙盒回放
   共用一份定义），`room-runner` 转出去保持老引用可用。沙盒为此去 import 整个
   B站 长连模块是明显不对的。
2. `map((s) => summarizeSession(s))`。**回调的参数个数是接口的一部分**，
   `map` 会多传两个 —— 任何 `f(x, now)` 形状的函数都不能直接当回调。
3. 文件名改用本地时间（和日志分片同一口径），README 里同时给本地时间和 UTC 两种写法。
4. `loadSeq` 序号守卫：只有最新一次的结果允许上屏；撞 429 时退避 700ms 重试两次，
   期间用户又点了别的就把机会让给新的那次。

**验收**：`check-report` 1 项（只送过礼也算来过）、`check-p0` 1 项（缺 `endedAt`
的封存场次时长不能是 0）、`check-p5` 1 项（文件名必须是本地时间）、
`check-web` 2 项（连点不串、429 自己重试）。

**反向验证**：沙盒改回只认 `ENTER`、`map` 去掉箭头函数、文件名改回 `toISOString()`、
删掉 `loadSeq` 守卫与 busy 重试 —— 对应的 5 条断言各自变红，其余不动。

## D79 · 复盘导出：生成放服务端，口径只有一份

战报只能在页面里看。想存档、发群里、打印出来，就得有一份文件。

**做法**：`core/export-report.mjs` 收 `reports / summary / series / warnings`，
吐一个完整 HTML 字符串；路由 `/api/reports/export` 只管取数据、套文件名、按附件返回。
前端只有一个按钮。

三个不做的事：

1. **不在前端拼。** 前端拼就要把 `yuan()`、`duration()`、按天聚合再算一遍 ——
   那是第二个真相。二代的金额分叉过两次（差 1000 倍），形态就是"两处各算一遍，
   平时看着一样，某天不一样了"。所以导出和页面共用 `computeReports()`。
2. **不引图表库。** 两张柱状图手写 SVG，和页面上的趋势图同一套几何思路。
   为两张静态图引几十 KB，还要处理它在文件里的加载顺序，不值得。
3. **不打包成 zip。** 单文件 HTML 双击就能看，发到群里不会被当成压缩包拦下来。

**安全**：导出页里有别人说的话（昵称、礼物名）。每一处插值都走 `esc()`，
文件里没有任何 `<script>`、没有外链，再叠一层 CSP meta。断言直接验
`<img src=x onerror=...>` 会被转成文字。

**一个自己踩的坑**：收入图最初写 `d.giftBattery + d.scBattery`，而
`buildDailySeries` 只给合计 `totalBattery`，没有 `scBattery` —— `NaN` 进了
`Number.isFinite` 过滤，整张图被当成"没有数据"，**不报错**。
现在断言里有一条"页面上不许出现 NaN/undefined"，专门守这类字段名取错。

**验收**：`check-report` 6 项（完整文档 / 无脚本无外链 / XSS 转义 / 数字同源 /
空数据不抛 / 文件名） + 路由层 1 项（Content-Type 与附件头）+ `check-web` 1 项
（导出带上当前范围）。反向验证：收入改回 `giftBattery + scBattery` → 对应断言变红。

## D80 · "启动过"和"起起来了"是两件事

`RoomRunner.start()` 原来第一行就 `this.started = true`，失败也不回滚。

后果不是"这次没起来"，而是**这间房永久废了**：再调 `start()` 直接 return，
于是它没有日志、没有长连、投影是空的，而 App 那边还以为它好好的。
页面切过去就是白屏，唯一的出路是重启进程 —— 用户不可能想到这一步。

改成：

1. 主体包在 try 里，catch 里 `this.started = false` 并拆掉半启动的宿主与连接
   （插件可能已经起了定时器，不清掉的话"重试"会得到两套实例，两边都在说话）。
2. `App.switchRoom` 遇到"登记了但没起来"的房间会先 `_reviveRoom()` 重试，
   再激活。用户点一下就是重试，不需要"关掉再打开"（关掉会连缓冲一起丢）。
3. 新开的房间如果启动失败，明确推一条 notice —— 否则页面切过去安安静静，
   看起来像"这个房间没人说话"。

**验收**：`check-rooms` 2 项（运行体失败后能再试、App 层再点一次真的重试）。
反向验证：删掉 `started = false`、`_reviveRoom` 直接 return → 两条各自变红。

## D81 · 旧连接迟到的 close 不许碰新连接的定时器

`_bindSocket` 的 close 回调原来是无条件 `_clearTimers()`，只有 `this.ws === ws`
那一句做了判重。

换凭据、假活重连、认证超时都会**主动换一条新连接**，而旧 socket 的 close
可能在新连接建立之后才到。那时 `_clearTimers()` 清掉的是**新连接**的心跳定时器 ——
而假活检测（90 秒无报文就重连）也挂在同一个定时器里。

结果是两个保护同时失效：不再发心跳、也不再自己发现假活。表现是
"界面显示已连接，但一条弹幕都收不到"，而且不会自己好起来 ——
和文件头注释里写的第 4 条注意事项**完全相反**。

修法：`this.ws !== ws` 直接 return（只记一条 debug），一行都不许动。
"防住一个已知问题"的代码，必须连同它的判断条件一起读一遍。

**验收**：`check-protocol` 1 项（假 socket + 迟到的 close，断言心跳还在、
没有多排一次重连）。反向验证：改回无条件 `_clearTimers()` → 变红。

## D82 · 总览：一眼看全部，但「没连上」必须自成一类

多房间真正的用处是"一眼扫过去"：哪间在动、哪间冷、哪间根本不在这儿。
之前这些只能一间间切过去看，房间列表还藏在弹窗里，只画一次快照。

现在点「换房间」= 房间总览：一间一行，右边四列（弹幕 / 礼物 / 人气 / 连接），
弹窗开着时每 2 秒刷一次，点一行就切过去。

三个决定：

1. **不做跨房间合计。** 只数"几间在跑、几间在播、几间没连上"。
   不同直播间的弹幕加起来说明不了任何事（`roomsList()` 里也有同样的注释）。
2. **「没连上」自成一类。** 一间解析房间号就失败（或断网、B站 接口抖）的房间，
   和一间"主播今天没播"的房间，`state` 都是 `offline`；只看这一列，
   用户永远分不清"等就有数据"和"等多久都不会有"。所以 `roomsList()`
   多报一个 `started`，总览用红点 + "没连上（再点一次会重试）"标出来，
   顶上再单独数一句"几间没连上"。**能看出来的故障，才叫故障。**
3. **只改数字，不重建行。** 每 2 秒重建整张表会换掉用户正要点的那颗按钮：
   mousedown 落在旧节点上、mouseup 时它已经不在文档里，`click` 不触发 ——
   表现是"点关闭没反应，要多点一下"。只有房间增减或当前房间变了才重建
   （签名 = `roomId + 是否当前`），其余就地改 `textContent`。
   这是 `panels.js` 一直在用的办法，只是这次差点忘了。

判断逻辑（在播 / 没连上 / 副标题 / 四列文案）抽进 `web/views/room-overview.js`，
是纯函数，`check-web` 直接喂假房间断言 —— 这些判断错了页面不会报错，
只会显示一个"看起来正常"的灰点加"未开播"。

**验收**：`check-rooms` 1 项（起失败的房间 `started=false` 且字段齐全）、
`check-web` 3 项（没连上不显示成未开播、汇总只数房间、字段缺失时不诬陷）。
反向验证：`roomsList()` 去掉 `started`、`buildRoomRows` 里把 `broken` 写死成
`false` → 各自变红。

## D83 · 回放要同时报「想说多少」和「发得出去多少」

沙盒回放不碰闸门（不能真发），于是它**看不见限速**。这不是理论问题：

拿真实日志量了一遍 —— 某一场（9,228 条事件）里，欢迎插件按当前配置"想说"
3,845 句，而日志里实际只有 1,806 条 `SENT`。差的那 2,000 多条不是插件没认领，
是闸门的最小间隔（1.2 秒）吃了：那个房间的进场速度远高于每秒一个。

也就是说，沙盒给出的"会发 3,845 句"是一句**看起来正常的假话**。
用户照着它调文案，上线只会出去一半，而界面上没有任何地方不对劲。

修法：新增 `simulateSendGate(said)`（`core/gate.mjs`），按**事件时间**把同一套
规则（最小间隔 + 同句去重窗口）重放一遍，回报"其中几句真能发出去"。
用事件时间而不是现实时钟：回放把几小时压进几十毫秒，用现实时钟会一句都发不出去。

两条刻意的边界：

- 参数从 `GATE_DEFAULTS` 读，**和线上共一份**。写两处的话，改了其中一处就会出现
  "回放说能发 100 条、实际出去 40 条"，这种差异既不会报错也没人会查。
- 没有时间戳的条目**不更新** `last`，否则它会把后面全判成超频（"算不准"不该装成"算准了"）。

验证：那场真实日志按事件时间折算得到 1,760 句，日志里实际 1,806 条 —— 差 2.5%
（闸门还允许高优先级消息等一个槽位，这条没模拟）。数量级对了，结论就是对的。

**验收**：`check-send` 3 项（同秒 10 句只放 1 句、去重窗口、缺时间戳不误杀）、
`check-report` 1 项（20 人同秒进场 → 说 20 句、真发 1 句）；`note` 里写明限速不在
插件侧，页面上直接显示"其中 N 条真能发出去（限速拦掉 M 条）"。
反向验证：把间隔判断短路 → 两条断言同时变红。

## D84 · 地址里坏掉的百分号编码是 400，不是 500

`/api/plugins/%E0%A4%A/config` 这种地址，`new URL()` 照收不误
（不完整的多字节序列它不管），而 `decodeURIComponent()` 会抛 `URIError`。

这个异常原来一路冒到 HTTP 层兜底：**500 + `internal_error` + 一整段堆栈**。
可服务端什么都没坏 —— 是请求方把地址写错了。报 500 会让运维去翻服务端日志找
一个不存在的问题；而且本机任何进程只要拼个坏地址就能把 error 日志刷满。

修法：路由解码时接住 `URIError`，转成 `400 / bad_path`，消息里带上那段原文。
判断"这是谁的错"比判断"抛没抛异常"更重要。

**验收**：`check-http` 1 项（`%E0%A4%A` 与 `%ZZ` 两种写法都必须 400 + `bad_path`）。
反向验证：改回直接 `decodeURIComponent` → 变红。

## D85 · 提醒只认边沿，重放和重启补的历史不许再响一遍

开播/下播提醒有三个"看起来该发、其实不该发"的时刻，判断全交给
`server/core/state-machine.mjs` 的边沿，`_notifyLiveEdge` 只消费边沿：

1. **重连后补发。** 断线期间的事件会重放；`LIVE_START` 再来一遍时，状态机
   发现"本来就在播"（liveTime 相同），根本不出边沿。按"收到 LIVE_START 就发"写，
   每次网络抖动都会提醒一次开播。同一条 seq 被重放也一样：投影幂等返回时
   不产生新边沿，调用方不能去读"上一次的边沿"。
2. **重启校准。** `_syncLiveState` 发现"启动前就在播"，补一条 synthetic 事件
   把投影拉回正确状态 —— 那是恢复记忆，不是刚发生的新闻，跳过。
3. **重连校准。** B站 重连后不补发断线期间的 LIVE / LIVE_END，只在 `start()`
   校准一次会让这段开播/下播永久丢失。所以每次 ready 都重新取房间信息并
   `_syncLiveState`；重连补的事件标 `inferred`：**要提醒**（它确实发生过），
   但下播结束时刻只能推断，投影同样标 `endedAtEstimated`，否则战报时长会当成精确值。
4. **webhook 失败。** 页内 toast 与外发是两条路：失败只记日志，不重试、不阻塞、
   不影响页内提示（页面上会多一条 warn 提示外发失败）。提醒丢了事小，
   把事件处理拖出队列事大。

配套的几条：

- 日志里的 webhook 地址只留域名。密钥在 query（企微/钉钉）或路径（飞书）里，
  原样打出来等于把机器人钥匙抄进日志，而日志是要导出、发给人看的。
- **HTTP 200 不等于发送成功。** 企微/钉钉/飞书在 key 失效、被限流时照样回 200，
  失败只在 `errcode` / `code` 里。`webhookError()` 按平台形状判定；
  自建网关的 `code: 200` 不误判为失败。
- 地址超 500 字符当场 400，不再 `slice(0, 500)` 悄悄截断；`_saveConfig()` 失败
  要回滚内存值并报 500，不能页面显示"已保存"、重启又变回去。
- webhook 地址是**写凭据**：开了访问口令时 `GET /api/notify` 也要 token；
  WebSocket 不受同源策略保护，upgrade 必须校验 Origin（与写接口同一套白名单）。

**验收**：`check-rooms` 覆盖同一条事件重放只响一次、synthetic 不提醒、inferred 要提醒、
非边沿重复 LIVE 不提醒、失败不拖垮通知、失败日志不含密钥、平台错误码、GET 口令；
`check-p0` 覆盖"幂等 apply 不交出旧边沿"与 inferred 下播的 `endedAtEstimated`；
`check-http` 覆盖跨站 Origin 的 WS upgrade 被拒；
`check-web` 覆盖提醒设置的 7 项交互（含迟到的 load 不覆盖已保存值）与"控件必须接到 app.js"的护栏。
反向验证：删掉 `if (rec?.payload?.synthetic) return;` 或让 `lastEdge` 直读 `sm.lastEdge` → 对应用例变红。

## D86 · 下播战报与提醒共用出口，但取数必须在边沿当下

战报不是第二套通知系统：配一次 webhook，开播/下播提醒与下播战报都走它。
`notifyReport` 默认关；开关必须和地址一起存在 —— 没地址单开返回 400，
清空地址自动把开关关掉，避免留下"看起来开了、其实永远发不出去"的半套配置。

三个关键决定：

1. **只在真实下播边沿发。** 复用 D85 的边沿语义：重启校准的 `synthetic` 不发
   （那不是刚下播），重连补的 `inferred` 要发（确实下播了，时刻是推断的）。
2. **数据源是投影快照，不是重放日志。** 下播这一刻日志里刚写进 `LIVE_END`，
   重放能得到同一场，但要多扫整个分片（消息晚到几十秒），还可能把下一场混进来。
   投影是事实的实时影子，这一场刚闭合，它最清楚。
3. **在边沿当下同步组装文本。** 提醒的 webhook 是 fire-and-forget，战报排在它的
   `.then` 里发送；如果战报的数据也到 `.then` 里再取，断线重连快的时候新一场已经
   开演，`snapshot()` 会换成新场，战报就成了一页空账。所以 `_buildLiveReport()`
   在边沿当刻同步取数、生成死文本，webhook 地址也一并捕获；之后投影怎么变都不影响。

发送顺序仍是「下播提醒 → 战报」：群里先知道下播了，再看这一场的账。
提醒失败也照样尝试战报 —— 两种消息各自有用；战报失败只补一条
「房间 X 的战报没发出去」，不回头影响已经发出去的提醒。

文案上宁可显得啰嗦，也不许把拍脑袋说成精确：`implicit`（没有 LIVE_START）标
「起点未知」，`endedAtEstimated`（结束时刻推断）标「约」。收入行只列非零项，
Top 送礼只统计礼物（舰长、SC 已在收入行里，不混进送礼榜）。

**验收**：`check-rooms` 8 项（文案 / 推算值 / 开关 / synthetic / 无投影 / 竞态 /
接口校验）；`check-web` 3 项（回填、保存、清空地址顺带关战报）；
反向验证：删掉 `notifyReport` 判断 → 「没开战报只发提醒」变红；
把战报组装挪进 `.then` → 竞态用例的「取数发生在边沿当下」断言变红。

## D87 · 续费舰长不能听「开通」

## D88 · 付费用户档案从日志重放，大额提醒只看单笔

「付费用户榜」要跨场次，而线上投影每场关闭后只保留刚封存的那一场，
跨场数据没有第二次来源。所以榜单和战报走同一条路：读日志、`buildPatrons`
按 uid 合并 —— 这样也保证榜上的金额和战报对得上，而不是页面上再算一遍。

金额口径：

- 免费礼物（`isPaid === false`）算次数、不计金额，和投影的 `giftBatteryOf` 一致；
- 舰长与 SC 直接用报文里的 `battery`；SC 缺电池时回落 `yuan * 10`（1 元 = 10 电池）；
- 匿名（uid 空 / `'0'`）不进榜：没有稳定的身份，合并了也是错的。

大额提醒：

- 只判断**单笔**（一条 GIFT / 一次 GUARD_BUY / 一条 SC），不累计。累计要维护
  跨场状态、还要决定「多久内算一次」；而「这一笔很大」本身就是可以立刻处理的信号。
- 阈值 0 = 关闭；页内 toast 永远发，配了 webhook 才外发，失败只补一条警告 ——
  和开播/下播提醒同一套失败语义。
- 文案带房间号：多房间是常态，只说「甲送出火箭」会让人以为是当前这间。
- 接口只收 0..`MAX_BIG_SPEND_BATTERY`（1e9）的整数；字符串不悄悄强转成数字，
  因为「10000」和 10000 之间的歧义应该由调用方解决。

**验收**：`check-patrons` 7 项（口径 / 窗口 / 排序 / totals）+ `check-rooms` 6 项
（阈值边界 / 0 关闭 / webhook 失败 / 落盘 / 两个接口）+ `check-web` 6 项
（打开、切窗口、保存、空状态、接线护栏）；反向验证：把免费礼物改回计金额、
把阈值判成 `<=`，各自变红。

## D89 · 醒目留言待读：清单从日志来，已读单独存

SC 的清单不能只靠内存：页面刷新、服务重启、切房间都会丢，而主播要在事后
补读。所以清单和付费用户档案走同一条路 —— 读日志、`buildScQueue` 过滤
`SUPER_CHAT`，按时间倒序取最近 500 条；金额口径与投影/战报一致（电池优先，
旧日志缺 `battery` 时 `yuan * 10`）。

几个边界：

- **未读数只数清单里截断后的条目**，不数窗口内的全部 —— 否则红点会显示
  “还有 3 条”，但列表里一条都找不到。
- 已读状态单独存 `data/sc-read.json`，只留最近 5000 个 id；id 自带房间前缀，
  多个房间共用一个集合不会串。再早的记录会重新显示为未读，这是文件长度的取舍，
  不是 bug。
- 徽标只在**实时事件**（`case 'event'`）里 bump；backlog 补发不 bump，
  否则刷新页面会把已经读过的旧 SC 又顶成未读。打开面板后一律以
  `/api/sc` 返回的 `unread` 为准。
- 换房间时红点清零：后台房间的旧未读不能挂到新房间头上。
- 标记已读接口先 trim 再校验 id 形状，空串/坏 id 当场 400；幂等 —— 重复标记
  返回 `marked: 0`，不报错。

**验收**：`check-sc-queue` 8 项（筛选 / 金额 / 排序 / 窗口 / 已读 / 名字回落 /
截断 / 异常输入）+ `check-rooms` 2 项（GET 503 与已读生效、POST 校验与落盘）
+ `check-web` 8 项（打开 / 切窗口 / 单条与全部已读 / 徽标 / 空状态 / 失败 /
接线护栏）。

## D90 · OBS 挂件单独成页：透明、只读、不碰主界面

直播画面里的挂件不能塞进观测台里做一个「全屏模式」：观测台有侧栏、按钮、登录和
大段 DOM，全屏之后还要藏一遍；而 OBS 的浏览器源只要一个能透明叠加的页面。

所以挂件是**独立入口** `web/overlay.html`：

- `background: transparent` + `pointer-events: none`。OBS 合成时不会盖住画面，
  鼠标点不到它，也就不可能误触。
- 不登录、不写配置：只连同源 WebSocket 读 `stats` / `event`，再每 60 秒拉一次
  `/api/patrons`。付费榜要重放日志，不能跟着 1 秒一次的 `stats` 刷新。
- 纯函数（金额 / 时长 / 礼物行）在 `overlay.js` 里导出；模块顶层用
  `typeof document === 'undefined'` 决定要不要启动 DOM 和连接。这样 node 自检
  可以直接 import，不需要一整套假浏览器。
- 不拖垮直播画面：WS 断线按 400ms×2^n 退避重连；付费榜读失败保留上一份；
  只有大额提醒会弹 8 秒横幅。挂件不该在画面中间报错。
- 礼物列只留最近 5 条、按 seq 去重；收到 `reset`（换房间）就清空上一间的礼物和
  时长，避免把 A 房间的数字挂到 B 房间头上。
- SW 预缓存清单显式加 `/overlay.html`：没有任何页面链接到它，只靠爬引用会漏；
  CSS / JS 则从 `href` / `src` 自动爬出来。

**验收**：`check-overlay` 11 项（金额 / 时长 / 三种付费礼物文案 / 非付费事件 /
开播清理 / 页面节点 / 透明与 pointer-events / WS 与付费榜接线 / 预缓存入口）+
`check-pwa` 的「web 下每个源码文件都在预缓存覆盖范围内」；反向验证：把
`pointer-events: none` 改成 `auto`，挂件样式断言变红。

## D91 · 本场礼物目标：按电池算、只认边沿、播报可关

目标不是"KPI"，是给直播间一个当场能看见的进度：观众知道离达成还差多少，
主播知道什么时候该说一句。因此：

- **按本场算，不跨场累计。** `giftBattery` 来自投影的当前场次；下播后新场从 0 开始。
  跨场累计会变成"永久目标"，一场没达成就一直挂在头上，反而没有激励作用。
- **只认礼物电池。** 上舰、SC 不进目标 —— 它们有自己的答谢动线，混进来会让
  "目标"变成"收入目标"，口径和页面上写的不一致。
- **30% / 60% / 80% / 100% 各播一次，同一场同一档只播一次。** 用
  `${roomId}:${sessionId}:${milestone}` 记在内存 Set（上限 500，超了清空）。
  投影重放、断线补发都不会重复喊；重启后新场自然重新开始。
- **一笔跨多档只报最高档。** `goalMilestone(before, after, goal)` 从低到高找
  越过的档，记住最高那个；`before = after - 本笔礼物电池` 从投影反推，不依赖
  额外的累加变量。
- **每一档可写自定义文案（留空用默认）。** 存在 `giftGoalTexts` 里，只认
  30/60/80/100 四个键、字符串、最长 80 字；支持 `{当前}`、`{目标}`、`{百分比}`
  三个占位符。允许主播按档位说不同的话，但键必须是固定档位，避免出现
  "说了一句永远不会触发的文案"。
- **页内提示固定，弹幕播报可关。** 页内是主播自己看的，必须响；公屏说话走
  `gate.say({ reason:'gift_goal', priority:1, maxWaitMs:5000 })`，排队等不到
  就跳过，不能拖住礼物处理。关掉播报后页内仍响。
- **目标 0 = 关闭，且播报开关一起收。** 接口只收 0..1000000000 的整数；
  `giftGoalAnnounce` 非 boolean 直接 400。保存失败回滚内存并报错，不能出现
  "页面显示已保存、重启后没了"。
- 挂件只读 `brief.giftGoalBattery`，不自己算；目标为 0 时整块隐藏，
  不在画面上留一条空进度条。

**验收**：`check-goal` 8 项（四档边界、跨档只报最高、自定义档位、金额不涨、
目标 0、默认文案、小数、占位符与空串回落）+ `check-rooms` 4 项（各播一次与重放
不重复、自定义文案、关播报仍提示、坏配置忽略、接口校验与落盘）+ `check-web`
7 项（回填单位与四档文案、保存换算、空值、0 强制关、失败保留、回车、接线）+
`check-overlay` 静态护栏。
反向验证：把 `goalMilestone` 的跨档逻辑改成命中最低档就返回，
「一笔跨多档只报最高」用例变红（actual 30，expected 100）。

## D92 · 付费用户回访：只看本场之前，只提醒一次，不往外发

**决定**：在付费用户面板里加一个「近 90 天累计满 ¥X」的回访门槛（默认 0 = 关）。
付费用户进房时，如果他在**本场开播之前**、近 90 天内累计付费过门槛，就弹一条页内提示。

- **数据从日志重放。** 投影的场次明细只有 `viewers` 和礼物的 `giftByUser`，

- **同一场同一人只响一次。** `房间:场次:uid` 记在内存 Set（上限 1000）。

- **只发页内提示，不写 webhook。** 开播/下播和大额是"需要立刻知道"的事；

- **门槛只收 0..1000000000 的整数，0 = 关闭。** 保存失败回滚并报错；

- 窗口固定 90 天，不做成可配项：回访提醒的价值在"最近还活跃的人"，

## D93 · 全量读日志加索引缓存，但日志仍是唯一事实

**决定**：`EventLog.readAll()` / `readAllAsync()` 增加一份进程内缓存，键是
「分片列表 + 每个文件的 size/mtime」。键不变就复用已解析事件，键一变就重读。

- **只缓存解析结果，不缓存统计。** 投影、对账、战报各自重算；缓存里只有
  `{seq,id,ts,type,payload,...}` 事件，避免"统计结果过了两道缓存"变成第二份真相。
- **失效不依赖主动通知。** 追加会让文件 size 变、归档会让分片列表变、外部手改
  文件会让 mtime 变；三者任一变化，键就不同。另外 `append()` 与 `archiveOld()`
  会显式清掉缓存，避免文件系统时间戳精度带来的擦边。
- **返回副本。** 调用方常对结果排序/过滤/`push`；返回 `events.slice()`，
  不能让人顺手改到缓存数组。代价是一次浅拷贝，远小于重新解析。
- **读取期间有追加就不缓存。** 读完再算一次键，只有与读前一致才写入；
  否则宁可下次多读一遍，也不给出一份"少了最后一条"的缓存。

**验收**：`check-p0` 1 项（第二次读命中、改返回值不污染、追加后立刻读得到）。
反向验证：把键改成常量并去掉 `append()` 里的显式失效后，追加用例变红
（actual 20，expected 21）。

## D94 · 审计补丁：备份只抄能读的配置，提醒只算当前这一间

**决定**：这一轮修的是"出错时把好数据一起弄坏"的几处边界，不改变功能语义。

- **`app.json.bak` 只备份能被 JSON 解析的配置。** 保存前先读一遍当前文件；
  手改坏的 app.json 不复制进 `.bak`，否则下一次用它恢复时会把坏文件当成"上一份"，
  两份一起坏。主配置与备份都读不出来时才按空配置启动，首次没有文件不算错误。
- **读日志缓存永远返回副本。** miss 路径返回的数组不能同时存进缓存——调用方
  `push` 一下，缓存就多出"事实里没有"的事件。缓存命中与未命中都 `slice()`。
- **回访索引只属于当前房间、当前这一场。** 后台房间开播不清当前房间的索引与去重集；
  投影的 `session` 还指着已封存上一场时不预热，避免离线进房被误报"回访"。
  预热失败要放掉 key，下一条 ENTER 会重试；去重集满了只丢最早一半，不清空。
- **礼物目标的过半/达成只对当前房间生效。** 后台房间的礼物推进自己的进度，
  但不该在当前页面上喊——观众分不清是哪一间的目标。
- **已读回滚要整份回滚。** `markScRead` 写盘失败时恢复到调用前的 Set，
  包括被 5000 上限挤掉的最早几条，而不是只删新增。
- **挂件换房立刻刷新付费榜**，不等 60 秒轮询。

**验收**：`check-rooms` 回访 3 项（后台开播、上一场不预热、预热失败重试）、
礼物目标 1 项（后台房间不喊）；`check-config` 备份用例；`check-p0` 缓存污染用例。
反向验证：去掉 JSON.parse、缓存存引用、去掉 `_isActive` 守卫，三处分别变红。

## D95 · SC 点歌：只认开头、队列单独落盘、动作即时生效

## D96 · 手机推送与 webhook 分开：目标是凭据，200 不等于送达

- **推送和 webhook 是两套配置。** 群里是存档、手机是提醒；接收人不同，
  合成一个开关必然让某一边收到不想看的东西。手机只推开播 / 下播 / 大额三类短消息，
  战报不推（长文本进锁屏只会被折叠）。
- **渠道 + 目标成对校验。** 只填 key 不选渠道、或选了渠道不填目标，都拒绝保存；
  不做"先存一半、发的时候再说"。
- **目标是凭据。** Bark key / ntfy topic / Server酱 SendKey 拿到就能往手机发消息，
  所以开了访问口令时，`GET /api/push` 也要口令（和 webhook 读接口同一条理由）。
- **三家形状分开写。** Bark 用 GET 路径 + title query；ntfy 用 POST 文本 + query title
  （标题走 header 会被 Node 的 ASCII 限制咬到）；Server酱 用表单 title/desp。
- **200 也可能是失败。** Bark 的 code≠200、ntfy 的 error、Server酱 的 code≠0
  都要在响应体里读出来；只判 `res.ok` 会得到"日志安静、手机没响"。
- **永不抛出。** 推送失败只补一条页内 warn，不拖垮提醒/大额通知本身。
- **测试按钮走真实发送。** 让用户在配完当场知道 key 通不通，而不是等下一次开播才发现。

**验收**：`check-push` 9 项（校验、三家形状、平台错误、网络失败、无 fetch）+
`check-rooms` 5 项（接口保存/400/落盘、开播推送、大额推送、失败警告、测试接口）+
`check-web` 6 项（回填、成对校验、保存、失败保留、测试结果、接线）。
反向验证：去掉 `_notifyLiveEdge` 里的 `_pushText` 调用后，「开播边沿推到手机」变红。

## D97 · 战报海报在浏览器画，不引服务端 canvas

- **不为了封面图破掉「唯一外部依赖是 ws」。** 服务端生成图片要么引原生 canvas，
  要么塞一个 headless 浏览器；只为一张 1080×1350 的图不值得。
- **数据就在卡片上，不再请求服务端。** 海报和页面必须是同一次计算的结果；
  重新调接口等于给"两个数字对不上"留后门。
- **推断值继续带限定语。** `implicit` → `≥`，`endedAtEstimated` → `约`，
  连接断了 → 「本场已中断」。海报比页面更容易被单独转发，更不能把推断装成精确。
- **文件名纯 ASCII。** `report-YYYYMMDD-HHmm.png`，不与上传端/系统的中文编码打架。
- **没有 canvas 就明确报错。** 不给空白图，也不假装下载成功。
- **画布只用最基础 2D API。** `roundRect` / `filter` 这类新接口在不同浏览器里支持度不一，
  海报糊一半比没有更难看。

**验收**：`check-poster` 8 项（文案字段、限定语、空场次、文件名、1080×1350 绘制、
toBlob 下载成功/失败、无 canvas 报错、reports.js 接线静态护栏）。
反向验证：把 `implicit` 的 `≥` 前缀去掉后，「推算起点加限定语」用例变红。

## D98 · 周报只在周一 10:00 推一次：没有出口就不开，数字从日志重算

- **周报必须有手机推送出口。** 没有出口时开启只会在无人看见的地方失败，
  所以保存时成对校验，启动时也把"只有开关、没有目标"的半套配置收掉。
- **只排一次，发完再排。** 不用 `setInterval`：机器休眠醒来可能一次补发好几条；
  每次只认"下一次本地周一 10:00"，正好卡点也顺延一周，避免同一分钟发两次。
- **只算当前活跃房间。** 当前日志读取路径只绑定一个房间；多房间周报需要
  另一套聚合口径，不在这一版里假装支持。
- **数字从日志重算。** 与场后战报同一套 `buildReports` → `weeklySummary`，

- **空周也发。** 「没有开播记录」是一句有效信息，沉默会被误认为服务坏了。
- **失败只记日志，不弹页内提示。** 周报在周一早上无人值守时发，补一条 warn
  页内提示也看不到；留在日志里可查即可。

**验收**：`check-weekly` 5 项（加法口径、五行文案、空周、周一 10:00 边界、跨月）+
