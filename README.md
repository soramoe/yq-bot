# 渔情B站直播助手机器人

> B站直播间机器人。**重写，不是演进。**
> 二代（`E:\渔月崽二代机器人`）继续独立运行，两边不互通、不共享代码。

---

## 为什么重做

二代的功能是够的，问题出在四个"隐式约定"：

1. 统计存在内存里，每 30 秒落盘一次 —— 直播中重启就丢整场，恢复只能靠猜
2. 插件有两份副本（`plugins/` 与 `plugin-catalog/`）—— 不同步就静默退回旧代码
3. `index.mjs` 3775 行、54 个手写 `if` 分支 —— 路由顺序成了隐式依赖
4. dryRun 有两个真相（设置项 + 控制台插件）—— 只好加补丁函数去对齐

三代把每一条都变成**显式契约**。

---

## 四条不可违背的设计原则

### 1. 日志是事实，统计是投影

所有事件**先落盘再处理**。任何统计数字都可以从日志重放算出来，
重启不需要"恢复"，重新 reduce 一遍即可。

> 推论：任何"内存里算着、定时存一下"的设计，一律不允许。

### 2. 内核管规矩，插件管玩法

| 归内核 | 归插件 |
|---|---|
| 发送闸门、免打扰、频率限制 | 欢迎、答谢、盲盒播报 |
| 模板渲染、占位符、冷却 | 关键词回击、补票 |
| 事件日志、状态机、认领仲裁 | 定时播报 |
| 配置 schema、dryRun | 守卫（但必须能一秒关掉） |

判据三问：**关掉它机器人还能跑吗？有人只想要一半吗？要能紧急单独关吗？**

### 3. 搬家和改行为，不在同一步做

每一步结束时，产品必须处于「可运行、可回退」的状态。
P3 之前，用户看到的行为应当零变化。

### 4. 不引框架，引抽象层

前端不换 React/Vue/Tailwind。把重复劳动交给 **schema**，
把人的精力留给战报这种真正需要设计的地方。

验收：**新增一个插件，前端代码改动 = 0 行。**

### 审计记录（2026-11-02）

83 项断言全绿的情况下做了一次对抗性审计，**找出 6 个 bug，其中 2 个致命**，
而且它们有一个共同特征：出问题时一行日志都没有。

| # | 问题 | 后果 |
|---|---|---|
| 1 | 日志尾部读不出 seq 时从 0 重来 | 之后**全部事件**被幂等判断当"已处理"丢掉，整场统计冻结 |
| 2 | 隐式场次把状态机强设为 live | 真 `LIVE_START` 不出边沿，**两场数据合并成一场** |
| 3 | seq 恢复只看最后一个分片 | 跨天文件损坏时无法回退到前一天 |
| 4 | 守卫金额两条路径口径不同 | 对账永远差一点，半年后才有人发现 |
| 5 | 下播后的延迟弹幕另起一段 | 每场之后多一个只有几条弹幕的"幽灵场" |
| 6 | `snapshot().title` 装的是 `liveState` | 读的人以为自己拿的是房间标题 |

修复方式不是打补丁，而是改语义：状态机从两态变**三态**
（`offline` / `live` / `live_unknown`），把"在播"和"场次起点确定"分开；
金额口径收敛成一个 `batteryOf()`，三条路径共用。

> 审计的方法论：跑测试只能证明"设计想到的路径是对的"。
> 要找 bug 必须反过来问 —— **什么情况下这段代码会给出错误答案，还不报错？**

   脚本打印启动成功然后什么都不做 —— 又是一次静默失败。
2. **停止会留一个暂停标记。** 否则你看门狗 5 分钟后把它拉起来，
   看起来像"停不掉"。手动启动会清掉标记：手动启动就等于"我要它跑"。

`scripts\README.md`。原来的 `E:\bot-ops` 脚本与 `E:\yuyue3` 目录联接

**战报不读内存统计，只读日志。** 这一条决定了它能对三个月前那场算出和当时一样的数，
也决定了进程重启、跨天、服务刚起来还没连上房间时，战报照样是对的。

每张场次卡片上有「时间轴」：点开把这一场按分钟切成格子，拖一条滑块往前回看 ——
第 20 分钟弹幕为什么涨、收入是哪一刻起来的、机器人当时说了什么。三条约定：

1. **格子是累积量**，所以最后一格必须等于战报卡片上的数字（自检逐字段比对）。
2. **喂投影按 `seq`，不按时间。** `Projection.apply()` 按 seq 去重，按时间排会让
   迟到的事件凭空消失 —— 不报错，只是数字少一点。这个坑踩过一次，记在 D71。
3. **柱子是"这一格新增"，由服务端算好**（`danmakuDelta`）。前端拿相邻两格相减，
   等于把累积量的定义再写一遍，改一处就会静默对不上。

战报顶上的**每日趋势图**是手写 SVG（`svgEl` + `createElementNS`），不引图表库：
这里只有一种图，为一张柱子图带进几十 KB 和一套样式体系不值得。三条约定：

1. **一根柱子都不许前端自己算。** 服务端按天聚合好（`buildDailySeries`），
   而且是从**战报摘要**聚合、不是从原始事件重算 —— 金额口径只有 `summarizeSession`
   一份。前端算一笔，就会和卡片、和汇总出现三个数。
2. **空的那天补 0。** 不补的话两根柱子挨着，看起来像"连着播了 N 天"。
3. **一次只画一个指标，不做双轴。** 弹幕几千条、收入几十块，双轴的比例怎么取都会误导；
   想看收入就点上面的"收入"切过去（不重新请求）。

前端三条约定：

1. **入库不限流，只在渲染层限流。** 二代的"事件流停在 20:47"就是限流写在了
   入库之前，重连补发的 60 条只放行 3 条，数据永久丢失。
2. **snapshot 与 event 两种更新模式分开。** 配置页整块替换，监控页增量追加。
3. **不用 innerHTML。** 页面显示的全是别人说的话（弹幕、昵称），
   用 textContent 构造节点，注入问题在结构上就不存在。

第 4 条从 P2.5 起加上：**配置改的是增量，不是整份。**

`data/app.json` 里 `plugins` 只存**用户动过的那几个键**。存整份的话，
用户第一次点开面板就会把当时所有默认值固化成"他的设置"，
此后插件升级改了默认文案，老用户永远看不到新文案，也没有任何提示 ——
这种"设置永远停在上一次打开的版本"的问题，不看代码根本发现不了。

配套两个约定：

- **启用状态与 `config.enabled` 是两件事。** 前者是"这个插件整个不参与"，
  后者是"这个插件的功能开不开"。混成一个开关，用户关掉再打开会发现
  自己的配置被动过。
- **回填服务端返回的值。** manifest 有 `min` / `max`，用户填 100000
  而实际生效 600，回显自己的输入等于显示一个假值。

│  ├─ core\              内核：事件日志、投影、状态机、闸门、插件宿主、观众簿、战报与更新包解压
│  ├─ bili\              B站 协议：HTTP、登录、WBI、拆包、归一化、长连
│  ├─ http\              接口表、静态文件、WebSocket、安全头
│  ├─ qr\                二维码编码与渲染（自实现）
│  ├─ login\             登录页
│  ├─ tools\             自检（*.test.mjs）与手动验证工具（含更新执行器 update-apply.mjs）
│  ├─ auth.mjs           凭证持久化
│  ├─ app.mjs            应用层：多房间起停与切换、配置、事件缓冲、状态聚合、广播
│  ├─ login-server.mjs   登录服务

│  │  └─ guard.mjs       上舰那条特殊路径
│  ├─ gift\              礼物答谢：连击合并、差值补数量
│  ├─ blind\             盲盒盈亏播报（抢在答谢之前，不播时让路）

│  ├─ autocall\          主动打招呼：定时从观众簿挑人，自己 @ 过去（默认关闭）

│  ├─ sw.js              Service Worker：离线壳（只缓存界面，接口一律不缓存）
│  └─ manifest.webmanifest  PWA 清单：名字、图标、standalone
└─ data\                 运行时产物（日志/凭证），不进版本库

**不要提前把目录建满。** 二代的经验：按想象搭架子会留下一堆用不上的空壳。

`data/` 里有真实数据，别提交：`auth.json` 是登录凭证，
`events/` 是事件日志。验证时采集的 `data/events/21452505/` 是一份真实弹幕样本，
留着给以后做沙盒回放当素材。

**日志只压不删。** 超过 30 天（`app.json` 的 `logKeepDays` 可改）的明文分片
在启动时压成 `YYYY-MM-DD.jsonl.gz`，读取时透明解压 —— 对账、重放、战报
都不需要知道某一天的文件是哪种格式。压缩后立即解压比对字节，
不一致就删掉 `.gz` 保留原件：宁可占空间，也不能出现"文件在、内容打不开"。

**观众簿只追加、超期整片删。** `data/roster/<房间号>/YYYY-MM-DD.jsonl` 一行一个人，
只存 uid、最后来访时间、当时的名字；同一天再来不写第二行。默认保留 90 天
（`app.json` 的 `rosterKeepDays` 可改，但别小于欢迎插件的 `returningDays`，
否则"多久没来算陌生人"会被剪枝悄悄截断）。它只回答「这个人以前来过吗」，
不记说过什么、不存弹幕内容；侧栏只显示「认识多少人」，不下发名单。
沙盒回放用内存簿，不会把历史事件写进这里。

**主动打招呼（自动）**：`plugins/autocall` 不用人点、也不等事件 —— 开播后每隔
`intervalSec`（默认 300 秒）自己从观众簿里挑一位观众，发一条带结构化 @ 的招呼。
两个时间窗一起限制候选：`withinSec`（默认 600 秒）只挑最近来过的，
`minAgeSec`（默认 20 秒）跳过刚进场那几十秒（欢迎插件刚 @ 过，不能连着两条弹幕点
同一个人）；`perUserCooldownSec`（默认 1800 秒）保证同一个人不被反复点。
默认**关闭**，在设置页「主动打招呼」里打开。自定义文案里 `{用户}` 会换成昵称，
**别自己写 `@名字`** —— B站 收到 `reply_mid` 会挂可点的粉色 @ 标签，写两遍就重复了。
它不认领任何事件（claims 为空），候选只读自观众簿，插件禁用、换房间、沙盒回放都不会
污染数据；同样走发送闸门，演练只记 SENT，被限速拦下不算点过名，下一个间隔会再挑他。

**续费舰长不听说「开通」**：`GUARD_BUY` 报文里有 `is_renew`（`normalize.mjs` 同时认
`is_renew` / `renew` / `is_renew_guard` / `auto_renew` / `auto_renewal`，以及名字里带
「续费」的情况）。欢迎插件 1.5.0 起把两种话分开：设置页「欢迎 → 续费舰长答谢语」，
默认「感谢 {用户} 续费{舰长}！」；留空会自动回落到上舰文案，宁可说得普通也不能不吭声。
它仍与首次上舰共用同一张冷却表，不会同一秒冒出两条欢迎。

**招呼文案预设**：`web/core/greetings.js` 是**唯一**一份文案库，五套风格
（轻松日常 / 整活玩梗 / 温柔治愈 / 抽签游戏 / 极简短句），出厂默认「轻松日常」，
不用自己想词。设置页「主动打招呼 → 招呼语」上方有「套用文案预设」下拉，
选一套就整包替换并保存，底下会写明当前用的是哪套（改过一句就显示「自定义文案」）。
插件运行时不认识"预设"：配置里就是明文文案数组，换文案不用改插件、也不用加接口；
manifest 的默认值由 `check:greetings` 逐句比对，改了文案包忘了改 manifest 会立刻变红。

预设句子一律**不写名字、不带 `{用户}`、按码位 ≤ 20 字**：结构化 @ 会由 B站 自己挂
粉色标签，写两遍就重复；不写名字还能让长度固定 —— 否则一个长昵称就能把整句顶过
弹幕上限被静默截断。所以预设全部控制在 10 字以内，给自定义文案留余量。
自检把这三条都钉住了（见 `check:greetings`）。

**弹幕指令**：`plugins/command` 认 `#帮助` / `#本场` / `#我来过`。
触发规则故意收紧成**整条消息恰好是 `#` + 一个词**（`#` 或全角 `＃` 都行，
中英文别名都认）：`#帮助 你好`、`刚才那个#帮助有点用` 都不算 ——
只要规则放宽成"包含"，热闹的房间里就会变成刷屏。这一点有一条反向验证：
换成宽松匹配，那条真实弹幕立刻被吃掉。

`#本场` 只读当前场次的投影（弹幕 / 进场 / 观众 / 礼物 / 舰长 / SC），
`#我来过` 只 `peek` 观众簿 —— 指令插件不改任何状态，因为这是**观众能触发**的功能，
不该顺带改统计或往簿子里写东西。`#我来过` 用的是 `previousSeenAt`
（这一次之前的那一次），不是 `lastSeenAt`：后者对在场的人恒等于"刚才"，
拿它回答永远是"今天"，等于没回答。

频率有两道闸门：插件自己的 `cooldownSec`（同一人，默认 15 秒）和内核发送闸门。
冷却期内**仍然认领但不说** —— 认领是"我看过了"，不是"我必须说"，
否则这条弹幕会漏给关键词回击再回一遍。

**访问口令 / 检查更新 / 诊断包（P5）**：观测台只绑 `127.0.0.1:8900`，但本地端口
挡不住浏览器 —— 你打开的任何一个网页都能向它发 POST。所以第一道防线是 **Origin 检查**
（默认开，跨站一律 403），第二道是**可选的口令**（默认关，开启后写操作要带
`X-Access-Token` 自定义头；用自定义头而不是 Cookie，是因为 Cookie 跨站也会被自动带上）。
口令只存 scrypt 加盐哈希，`data/access.json` 被整个复制走也拿不到原文；
关掉是删文件而不是写 `enabled:false`。侧栏「访问口令」可开启 / 解锁 / 修改 / 关闭，
连续输错 5 次退避 30 秒。

设置页「维护」里现在有**检查更新 / 下载更新包 / 重启并应用**，以及**下载诊断包**。更新仍然**不后台静默安装** —— 半夜自动装失败，第二天开播发现机器人起不来，是这类工具最典型的死法。区别是：下载完先校验 `sha256` 和大小，再由独立进程 `server/tools/update-apply.mjs` 执行「等旧进程退出 → 备份 → 替换 → 启动 → 健康检查」，起不来会自动还原上一份。只替换代码与文档条目（`server/`、`web/`、`plugins/`、`docs/`、`package*.json`、`README.md`、`.gitignore`），`data/` 永远不动。直播中点「重启并应用」会再确认一次，确认前不会停服务。

更新源兼容旧清单 `{version, notes, url}` 和 v2 清单 `{version, notes, url, download, sha256, size, minVersion}`；只有 v2 带 `download` 时才出现下载按钮。默认没有更新源（没发布到 npm，也没有固定 Release，写死地址只会永远 404），没配时会明确说「尚未配置更新源」，不假装检查过了。诊断包是**要发给别人**的东西，
所以按**白名单**构造：Cookie / 口令一个字节都不进包，观众昵称与弹幕正文不进包，
观众 uid 只留 sha256 前 8 位（能看出是不是同一个人，无法反查），自己的昵称打码成首字。
包里是零依赖手写的 store 模式 ZIP。

## 发布新版本 / 一键更新

发布只走 GitHub Releases，不用 npm，也不依赖 GitHub API 查版本：

```bash
# 1. 改 package.json 的 version（例如 0.3.0），提交
# 2. 打 tag 并推上去，Actions 会自动打包
git tag v0.3.0
git push origin main --tags
```

`.github/workflows/release.yml` 会：校验 tag 与 `package.json` 版本一致 →
`npm ci --omit=dev`（把唯一的依赖 `ws` 一起打进去）→ 打成
`yuyue3-<version>.tar.gz`（排除 `data/`、`.git/`、`.github/`）→ 生成
`latest.json` → 创建 Release 并上传两个文件。

更新源填这个固定地址（`<owner>` / `<repo>` 换成自己的）：

```
https://github.com/<owner>/<repo>/releases/latest/download/latest.json
```

清单格式（v2；旧格式 `{version, notes, url}` 也能读，但不会出现下载按钮）：

```json
{
  "version": "0.3.0",
  "notes": "本版改了什么",
  "url": "https://github.com/owner/repo/releases/tag/v0.3.0",
  "download": "https://github.com/owner/repo/releases/download/v0.3.0/yuyue3-0.3.0.tar.gz",
  "sha256": "64 位十六进制",
  "size": 1234567,
  "minVersion": "0.2.0"
}
```

维护页的流程是「检查更新 → 下载更新包 → 重启并应用」：

1. 下载到 `data/updates/<version>/package.tar.gz`，先校验 `sha256` 和大小，
   不对就不改名、不进下一步；
2. 真正确认后才拉起独立进程 `server/tools/update-apply.mjs`，服务这时才退出；
3. 执行进程等旧 PID 退出 → 备份到 `data/backups/<时间>/` → 替换
   `server/ web/ plugins/ docs/ package*.json README.md .gitignore` → 启动 →
   轮询 `/api/status` 30 秒；
4. 健康检查不过：杀掉新进程、还原备份、把旧版本拉起来，日志写在 `data/update.log`。

`data/`（登录凭证、日志、配置、已读状态、点歌队列）永远不在替换清单里；
备份只留最近两份。直播中点「重启并应用」会二次确认，不会静默重启。

## 装成 App / 离线能看

页面是 PWA：浏览器地址栏右侧会出现「安装」，装完就是一个独立窗口，任务栏/桌面上有图标。

| 能力 | 说明 |
|---|---|
| 离线打开 | 断网（或服务没起来）时打开，界面照常出现，顶部会挂一条「离线 · 界面来自缓存，数据停在断开前」 |
| 数据不缓存 | `/api/` 与 WebSocket **一律直连**。宁可报错，也不给一份看起来正常的旧数字 |
| 网络优先 | 能连上就用新代码，连不上才用缓存 —— 零构建没有内容哈希，缓存优先会一直给旧版本 |
| 自维护清单 | 没有打包器，SW 安装时顺着 import / `href` 自己爬一遍依赖，加模块不用记得改清单 |

改前端之后**不用**手动升版本号：下一次请求就是新的。
只有"壳的入口文件换了"这种语义变化才需要动 `web/sw.js` 里的 `VERSION`。

图标是脚本生成的（零依赖，不引 sharp/canvas）：

```bash
npm run icons        # 重新生成 web/icons/*.png
```

注意：Service Worker 只在 `localhost` / `127.0.0.1` 或 HTTPS 下可用。
直接用 `file://` 打开页面是没有离线能力的（也不该有）。

## 同时盯多个房间

点右上角「换房间」打开**房间总览**：

- 每间一行：状态点 · 房间号 · 标题，右边四列是**本场弹幕 / 礼物 / 人气 / 连接状态**；
- 弹窗开着的时候每 2 秒刷新一次 —— 多房间的用处就是"一眼扫过去"，只画一次快照等于看历史；
- 点「切到这间」切过去；下面输入框填房间号就**再加一间**并切过去；
- 每行右边有「关闭」，只剩一间时这个按钮是灰的（全关掉之后页面就没有数据源了）。

刷新的实现上有两个刻意的取舍（D82）：

1. **只改数字，不重建行。** 每 2 秒重建整张表会把用户正要点的那颗按钮换掉
   （mousedown 落在旧节点、mouseup 时它已经不在文档里，click 不触发，表现为"点了没反应"）。
   只有房间增减或切换当前房间时才重建。
2. **「没连上」自成一类。** 一间解析房间号就失败的房间，
   和一间"主播今天没播"的房间，`state` 都是 `offline` —— 只看这一列根本分不清。
   所以 `roomsList()` 额外报 `started`，总览用红点和"没连上（再点一次会重试）"标出来。

三条行为约定：

1. **切换只是换视图。** 后台那间继续收弹幕、继续记日志、继续跑插件，
   切回来是毫秒级的事 —— 不重连 B站、不重放日志，也不会在那一场中间留个洞。
2. **数字不混。** 每条事件都记在**它自己那个房间**的缓冲里，页面只显示当前这间。
   两个直播间的弹幕加起来没有意义，所以也不做任何合计。
3. **切换会清空页面。** 事件流会重连并按新房间的 seq 重新补发 ——
   不这样的话，新房间的第一条弹幕会接在旧房间的尾巴上，看起来像"这间已经有这么多弹幕"。

上限 10 间（`MAX_ROOMS`）。插件配置**不分房间**：文案属于主播的人设，
换个直播间不该变成另一套话（Q7）。

## 开播 / 下播提醒

页内提示一直有；想推到手机或群里，在「换房间 → 房间总览」最下面填 webhook 地址，
点「保存」即可。清空再保存 = 关闭外发。

地址下面还有一个「下播后把本场战报发到同一个 webhook」：勾上以后，每次**真实下播**
（不是重启校准、不是重连推断）先发下播提醒，紧跟着发这一场的战报。战报包含时长、
观众、弹幕、礼物 / 舰长 / SC 三项收入与总收入，以及礼物送礼 Top 3（只统计礼物，
舰长与 SC 只在收入行里）；起点未知或结束时间是推断的，会在时长前标「约」并注明。
战报取数发生在下播边沿**当下**，不重放日志 —— 否则提醒的 webhook 一卡，期间重连
开了新一场，战报就会变成新场的空账。提醒发送失败也照样尝试战报；战报自己失败只
补一条「房间 X 的战报没发出去」，不影响已经发出去的提醒。

- 支持企业微信、钉钉（`{ msgtype, text: { content } }`）和飞书（`{ msg_type, content: { text } }`）；
  认不出的地址按企微/钉钉形状发，自建网关大多认这个。
- **只在边沿提醒**：`offline → live` 与 `live → offline`。同一次开播重复推 LIVE、
  断线重连后补发的旧日志，都不会再响第二遍。
- 重启时补出来的是 `synthetic` 事件（"它本来就在播"），不是此刻发生的，不提醒。
  之后每次连接就绪都会再校准一次，补出的边沿一律标 `inferred`：B站 不补发断线期间
  的 LIVE / LIVE_END，这段时间确实发生了，所以要提醒；启动后几秒内开播的情况也走
  这条路 —— 否则真正的 LIVE 会被同一 `liveTime` 去重，这条开播提醒就永久丢了。
  `inferred` 的下播时刻是推断的，战报里的时长会标「约」。
- 标题包在 ROOM_CHANGE 里、可能比 LIVE 晚到 —— 没有标题就只说房间号，不硬凑。
- 外发是尽力而为：8 秒超时，失败只记一条 warn，不影响页内提示和收弹幕；
  页面上会再补一条「webhook 没发出去」，不能让人以为群里收到了。
  日志里的地址只留域名（query / 路径里就是密钥）。
- 平台回 HTTP 200 不等于发成功：企微/钉钉看 `errcode`，飞书看 `code`，非 0 一律算失败。
- 地址最长 500 字符，超了当场拒绝，不会悄悄截断；保存不进 `data/app.json` 会回滚并报错。
  启动加载配置时，坏掉或超长的地址同样会被忽略并记一条 warn，不拿半截 URL 去请求；
  没有有效地址时，战报开关自动收掉。
- 战报开关存在同一个 `app.json` 的 `notifyReport`（默认 `false`）。没填地址只勾战报
  会当场 400：发不出去的开关比没有更糟；清空地址会自动关掉它，不留半套配置。
- 地址存在 `data/app.json` 的 `notifyWebhook`。它本身就是写凭据 ——
  开了访问口令时，读它也要口令；WebSocket 升级请求同样校验 Origin。

## 付费用户档案与大额提醒

顶部「付费用户榜」按 uid 跨场次合并付费贡献：礼物、舰长、醒目留言三类分开记，
免费礼物算个数但不计金额（和投影、战报同一口径）。榜上显示最近一次消费时间，
可切「最近 7 天 / 30 天 / 全部」；上限 200 人，默认取前 30。

数字来自服务端重放日志（`/api/patrons`），不是拿线上投影再算一遍 ——
投影每场会换，跨场的数据只能从日志来；这也保证榜上的金额和战报对得上。

同一个面板里还有「单笔大额提醒：满 ¥X」：

- 只按**单笔**判断（一条礼物 / 一次上舰 / 一条 SC），不看累计；
  0 = 关闭。输入单位是元，发给服务端前换算成电池（1 元 = 10 电池）。
- 触发时页内 toast 一条「【大额】房间 X · 谁 送了什么（¥金额）」；
  配了提醒 webhook 就同一条发到群里。失败只补一条警告，页内提示照响。
- 免费礼物金额是 0，不会提醒；金额为 0 的旧日志同样不会。
- 阈值存在 `data/app.json` 的 `bigSpendBattery`（默认 0），接口只收
  0..1000000000 的整数；字符串会被当成参数错误，不会悄悄强转。

同一个面板里还有「回访提醒：近 90 天累计满 ¥X」：

- 只在**本场开播之前**付过钱的人进房时提醒；本场刚送过礼的人不算回访，
  那是正在发生的事，大额提醒/答谢已经在处理。
- 窗口固定 90 天，按 uid 累计礼物 / 舰长 / SC 的电池；门槛 0 = 关闭，
  默认 0（不打扰）。输入单位是元，保存时换算成电池。
- 同一场同一个人只响一次；只发页内提示，不往 webhook 发 ——
  避免「老观众来了」和真正的开播/大额通知混在群里。
- 索引在切房/开新场/改门槛时重建；门槛存在 `data/app.json` 的
  `patronReturnBattery`（默认 0），同样只收 0..1000000000 的整数。

## 醒目留言待读

顶部「醒目留言」把日志里的 SC（`SUPER_CHAT`）按时间列出来，默认看最近 30 天，
可切「最近 7 天 / 全部」；一次最多 500 条，更早的记录不进当前列表。
金额口径和战报一致：优先报文里的电池价，旧日志缺 `battery` 时按 1 元 = 10 电池折算。

- 每条可以单独点「已读」，也可以「全部已读」；已读状态存在 `data/sc-read.json`，
  换页面、重启都还在。
- 面板关着时来了新 SC，按钮上的红点会自己加一；打开面板后以服务端未读数为准，
  已读过的旧 SC 不会又被顶成未读。
- 已读 id 只留最近 5000 条；再早的记录会重新显示为未读 —— 这是防止文件无限长的取舍。
- 换房间时红点清零，后台房间的旧未读不会挂到新房间头上。

## 弹幕点歌

观众发一条内容以「点歌」开头的弹幕（如 `点歌 晴天`），就会进点歌队列。
只认弹幕：点歌是免费互动，醒目留言不参与，也没有金额这一列。

- 只认**当前房间**：后台房间的弹幕不会突然出现在页面队列里。
- 同一个人点同一首歌、且还在队里时不会重复加，也不会重复播报。
- 队列存在 `data/songs.json`，重启后还在；最多 100 首，满了先丢已完成的，再丢最老的。
- 顶部「点歌队列」按钮上的数字是**还在排队**的条数，不含播放中那条。
- 面板里可以「播放 / 完成 / 跳过」：播放会把上一条放回排队，完成和跳过直接从队列移除；
  动作立即落盘，失败会整份回滚并提示，不会出现页面显示成功、重启后又回来。
- 进队会 @ 点歌的人播一句「已点歌：xxx」，不带「下一首 / 第 N 位」这类位置后缀；
  点「播放」会播「接下来播放：xxx」。两句都走正常发言队列（优先级 1，最多等 5 秒），
  说不了话不会卡住礼物/SC 处理。

## 手机推送

开播、下播、大额这三类短消息，除了页内提示和 webhook，还能直接推到手机。
和 webhook 是**两套独立配置**：群里和手机上不是同一拨接收人，混在一起总有一边被吵到。

支持四家，在「房间总览」里选：

- **Bark（iOS）**：填 App 里的 key，或完整的 `https://api.day.app/<key>`。
- **ntfy（全平台）**：填 topic，或自建服务的完整地址；手机装 ntfy App 订阅同一个 topic。
- **Server酱（微信）**：填 SendKey，消息到绑定的微信。
- **Telegram**：填 `bot_token|chat_id`（token 从 @BotFather 拿；chat_id 可先给 bot 发条消息，再用 `getUpdates` 查）。

配置要点：

- 渠道和目标必须成对：只填渠道不填目标、或只填目标不选渠道，保存都会当场拒绝。
- 目标是凭据（拿到就能往你手机发消息）；开了访问口令时，读这项配置也要口令。
- 平台常常 HTTP 200 却在 body 里报错（key 失效、额度用光），所以 200 不等于送达；
  失败会在页面上补一条「手机推送没发出去：…」，不影响提醒本身。
- 配好后点「发测试」会真的推一条测试消息；发送结果（成功 / 平台错误）会直接提示。
- 战报不推手机：那是长文本，适合群里存档，塞进锁屏通知只会被折叠。

## 服务健康告警

页面上方有一个状态灯（默认不显示），出问题时变红；配了手机推送的话，
同一句话也会推到手机。它只回答一个问题：**再不管，今晚这场会不会悄悄废掉？**

会报的三种情况：
- 弹幕连接 `error` / `closed`，或重连超过 5 分钟还没好；
- 直播中 15 分钟没收到任何事件（可能断流，也可能真的没人说话）；
- 最近 10 分钟内写日志失败过（这一段复盘会缺）。

不会刷屏：同一类问题 30 分钟内只提醒一次；问题自己好了就清掉去重，
下次再坏会重新提醒。只对当前房间判断——后台房间断线不该在主播页上
闪红灯。

`data/app.json` 里 `healthAlert:false` 可以整组关掉主动提醒；`GET /api/health`
仍然返回状态，给外部监控用。

## 周报自动推送

手机推送配好之后，可以勾上「每周一 10:00 把最近 7 天的周报推到手机」。
一周一条，内容压成五行：场次与时长、弹幕 / 进场 / 涨粉、三类收入、总收入。

- **没有手机推送就不能开**：周报没有别的出口，开了也只会静默失败，所以成对校验。
- **只算当前活跃房间**的日志；多房间各开各的周报不在这一版里。
- 时间按**本地时区**的周一 10:00；正好卡在 10:00 那一秒也不会重复发。
- 数字从日志重算（和场后战报同一套口径），不读内存里的实时统计。
- 最近 7 天一场都没播，也会发一句「没有开播记录」——沉默比空消息更让人以为坏了。

## OBS 场景联动

房间总览里能填 OBS WebSocket 地址、密码和两个场景名；开播时切到「直播中」，
下播切回「闲聊」。OBS 28+ 自带 obs-websocket，默认地址 `ws://127.0.0.1:4455`。

- **只在边沿连一次，切完就关**：不常驻长连接，不用处理 OBS 重启、密码变更后的重连；
  一小时连两次的代价可以忽略。
- **只在开播 / 下播边沿切**：重连重放的 LIVE 不会重复切场景；同一场景连续切会被跳过。
- **密码只进不出**：存在本机 `data/app.json`，页面读回来只有「设过没有」；
  留空表示不改，想清空有单独的按钮。
- **地址写坏整组忽略**：启动时 `ws://` 或 `wss://` 不合法就 warn 并关掉联动，
  不拿半套配置去连。
- **OBS 没开不影响直播**：连不上、密码错、场景名不存在都只记一条 warn，
  提醒、统计、战报照常。

## 主动招呼的在线确认

B站 的结构化 @ 只对**发送那一刻还在房间**的人生效；人已经走了，服务端会把
`reply_mid` 归零，观众看到的是一条没有 @ 的弹幕（有时只剩一个空位）。
「最近说过话」只能证明几十秒前在，不能证明现在还在。

所以发主动招呼前先查一次**高能榜**：

- **榜上命中**：只传 `reply:{uid,uname}`，正文不再重复名字，让 B站 自己挂可点标签。
- **没命中 / 查失败**：正文把名字写进句首，**不传 reply**，发一条普通弹幕；
  宁可没有 @，也不要在观众脸上留一个空位。
- **不是完整在线名单**：榜单只有消费靠前几十人，没命中不等于已离开，
  所以只把「命中」当可靠信号，绝不因为没找到就跳过这个人。
- **45 秒缓存**：成功与失败都缓存；直播中不能每个候选都打一次接口，
  失败时按「无法确认」降级，不影响开口。

实现位置：`server/bili/rank.mjs`（解析 + 请求）、`server/room-runner.mjs`
（缓存与 `hasOnline`）、`server/core/plugin-host.mjs`（`ctx.presence`）、
`plugins/autocall/plugin.mjs`（命中/未命中的文案与 reply 选择）。

## PK 情报

顶部「PK 情报」按钮，填一个对面房间号（真实号或短号都行），保存后每 60 秒
拉一次对面的公开信息，和自己的房间摆在一起：

- **只看公开数据**：标题、直播状态、人气、粉丝数、高能榜前几。
  不读对面的弹幕，不猜比分，也不自动往对面发任何东西。
- **首次不喊**：第一次拉到的数据只用来建基线；之后只在对面
  **未开播 → 开播**、**开播 → 未开播** 的边沿提醒一次，一直开着不会每轮都喊。
- **失败不编数**：拉不到就保留上一次快照，超过 3 分钟标记为「可能过期」，
  页面显示提示，而不是拿旧数字当现状。
- **提醒走现有出口**：页内 notice + 手机推送（配了才发），不额外开一套通知。
- **关掉就停**：房间号清空即关闭轮询，切房不会串到别的房间。

实现位置：`server/core/pk.mjs`（纯函数）、`server/app.mjs`（轮询与边沿）、
`server/http/api.mjs`（`/api/pk`）、`web/views/pk.js`（面板）。

### 开场自动播报

面板里可以开「开场 PK 时自动播报对面情报」。检测不靠弹幕报文，而是每 60 秒
拉当前房间的 `getInfoByRoom`：`pk_info_v2.pk_basic.pk_id` 变了就是新一场，
指定 PK、随机匹配、多人 PK 都是同一个结构。

播报分四段，中间停约 2.5 秒：

1. `迎战主播：<名字>`
2. `在线人数：<人数>`（取 `getOnlineGoldRank` 的 `onlineNum`，不是直播间人气；拉不到就说「暂时看不到」，不编 0）
3. `前十贡献：<合计>`（`getOnlineGoldRank` 前十条的 `score` 相加）
4. 达到阈值说强，否则说一般（强/弱文案都能在面板里改）

前三条整句都能在 PK 面板里自定义，但必须保留 `{名字}`、`{人数}`、`{贡献}` 占位符，
播报时会替换成实时数据；删掉占位符就不知道该把数字放哪，保存时会拒绝。

**播报前先把发言队列压住**：四段没说完之前，进场欢迎、关键词回复、定时问候
这些插件发言直接跳过，不排队 —— 排队的话会在四段结束后一起涌出来。
阈值默认 1000，`0` 表示永远算一般；同一场 `pk_id` 只播一次，PK 结束后清空，
下一场重新播。

## 下播战报海报

「场后战报」里每一场卡片上多了一个「海报」按钮，点一下生成 1080×1350 的 PNG，
可以直接发动态、发群，不用截图拼图。

几条规矩：

- **数字就用卡片上那一份**，不重新请求、不重新统计。海报和页面上的数字必须一模一样，
  多算一遍就多一个对不上的机会。
- 起点未知的场次显示 `≥`，结束时间是推算的显示 `约`，连接断了显示「本场已中断」——
  不把推断值装成精确值。
- 热门礼物最多列三条；收入按 10 电池 = 1 元换算，和页面口径一致。
- 文件名是 ASCII 的 `report-YYYYMMDD-HHmm.png`，避免上传端的编码问题。
- 浏览器不支持 canvas / 导出时直接报错提示，不会给一张空白图。

## 高光时间轴

一场播完，战报卡片上有「高光」：不用自己拖时间轴，直接给出值得回看的
12 个瞬间，按时间排好。

**怎么挑**
- 醒目留言 > 上舰 > 礼物，金额越高越靠前；免费礼物不计金额，不进榜。
- 再补两处弹幕最密的时刻，免得整张单子只剩"谁送了钱"。
- 选完按时间升序排回去——剪辑是从头往后看的，不是按金额看。

**怎么用**
- 每行是 `21:05 · +12 分 34 秒 · 事件`，点「复制」拿到这一行；
- 「复制全部」一次贴给剪辑或自己留档；
- 没有花钱事件也没有明显高峰时，明确写"没有"，不编一条出来；
- 超出上限（一场 12 个）时只保留分数最高的，页脚会说明这是挑过的。

数字和时间全来自时间轴那份 `/api/timeline`，不会再算一套金额——同一场
不能出现"时间轴上 ¥12、高光里 ¥15"这种事。

## 月报 / 季报

战报面板右上角有一个「月报 / 季报」：按**自然月**或**自然季**把场次加起来，
再和上一段做对比。不是"最近 30 天"，是 11 月 1 日到 11 月 30 日这种边界，
跨年也对（1 月的上期是去年 12 月）。

看的东西和战报一致：场次、时长、总收入（礼物 / 舰长 / 醒目留言分开）、
弹幕、进场、涨粉。对比只比有意义的几项；上期是 0 时显示「上期没有记录」，
不编一个 +∞%。

「复制文本」拿到的是可直接发群里的几行：

```
【月报】2026 年 11 月
场次 17 · 时长 19 小时 8 分 · 弹幕 2421 · 进场 162 · 涨粉 2
收入 ¥53.2（礼物 ¥49.2 / 舰长 ¥0 / 醒目留言 ¥4）
比上期：收入 +12% · 弹幕 +8%
```

数字全部由服务端从日志重算，前端不再加一遍。没有开播记录时直说
「这段时间没有开播记录」，不生成一张全是 0 的假报表。

## OBS 直播挂件

操作台是给自己看的；挂件是给**观众**看的。两者是两个页面，互不影响：

```
http://127.0.0.1:8900/overlay.html
```

在 OBS 里加一个「浏览器源」，填这个地址，宽高按 1920×1080 建，背景会自动透明
（页面本身是 `background: transparent` + `pointer-events: none`，不会挡住下面的画面，
也不会因为误点跳到别的页面）。

挂件上有什么：

- 左上：房间标题、直播状态、已经播了多久；
- 左下：本场弹幕 / 观众 / 进场 / 礼物 / 醒目留言五个数字；
- 右上：付费用户 Top 5（跟「付费用户榜」同源，60 秒刷新一次，不每秒重放日志）；
- 右下：最近 5 条付费礼物 / 上舰 / SC；
- 数字上方：设了本场礼物目标时多一条进度条，实时显示「已收 / 目标」；
- 中间上方：收到大额提醒时闪一条横幅，8 秒后自己消失；
- 没开播时显示一枚「未开播」的小提示。

几条约定：

1. **只读。** 挂件不登录、不写配置、不点已读；服务没开就只是连不上。
2. **数据同源。** 数字来自同一条 WebSocket 的 `stats` 广播，金额口径和战报、榜单一致
   （10 电池 = 1 元），不在页面里另算一套。
3. **不拖垮主流程。** 付费榜拉取失败就留着上一份，不往直播画面上弹错误。
4. 换房间时挂件收到 `reset` 会清空上一间的礼物和时长，再按新房间重连。

### 主题与场景

同一个挂件页，外观靠地址参数选，不用改配置也不会影响操作台：

```
http://127.0.0.1:8900/overlay.html?theme=light&scene=compact
```

- `theme`：`default`（深色玻璃）/ `light`（浅色卡片）/ `warm`（暖色）/ `mono`（高对比黑白）。
- `scene`：`full`（全部）/ `compact`（只留标题和数字）/ `minimal`（只留标题和临时横幅）。
- `hide`：`paid`、`gifts`、`goal`、`stats`，用逗号分隔，单独关掉某一块，
  其余布局不动，例如 `?hide=gifts,paid`。

参数拼错、写了不认识的值，会安静地回落到默认主题和完整场景——主播手改地址时
不该因为一个词拼错得到一块白屏。主题只换颜色，不改布局，也不改任何数字口径。

## 本场礼物目标

在「房间总览」里设一个本场目标（单位：元，0 = 关闭），直播时就会盯着本场
礼物电池的累计值：

- 30% / 60% / 80% / 100% 各播一次；同一场同一档只播一次，
  断线重连或日志重放不会又喊一遍。
- 一笔礼物同时越过几档时只播最高的那档，不会连着喊几句。
- 每一档可以写一句自定义文案（留空用默认），支持 `{当前}`、`{目标}`、`{百分比}`
  三个占位符；文案存在 `giftGoalTexts` 里。
- 目标按**本场**算，下播重开清零；中途改目标也会按新值重新判断，
  已经播过的档位不会因为改小目标而回退重播。
- 页内提示（toast）固定会响；「到 30% / 60% / 80% / 100% 时在弹幕里播报」是单独的开关，
  关掉后只是不在公屏说话，页内仍有提示。
- 弹幕走正常的发言队列（`reason: gift_goal`，优先级 1，最多等 5 秒），
  不会因为说不了话卡住礼物处理。
- 目标存在 `data/app.json` 的 `giftGoalBattery`（0..1000000000 的整数）
  与 `giftGoalAnnounce`；目标为 0 时播报开关自动收掉，避免留下永远不触发的开关。
- OBS 挂件会读 `brief.giftGoalBattery`，在五个数字上方画进度条；
  目标为 0 时整块隐藏。

## 导出复盘页

打开「场后战报」→ 右上角「导出复盘页」，得到一份**单文件 HTML**：

```
yuyue3-report-7734200-2026-11-05_06-19.html
```

双击就能看，不需要服务在跑，也不需要联网 —— 里面：

- 汇总卡（场次 / 总时长 / 弹幕 / 进场 / 礼物 / SC / 大航海 / 总收入）；
- 两张柱状图（每天弹幕、每天收入），内联 SVG，鼠标悬停有日期和数值；
- 场次明细表（开始时间、时长、各项数字、峰值人气、备注、热门礼物）；
- 需要说明的数字（比如旧版本采集的 SC 金额偏低）。

几条硬约定：

1. **数字和页面上的战报同源。** 导出走的是同一个 `computeReports()`，
   不是"前端再算一遍"（D79）。
2. **零脚本、零外链。** 没有 `<script>`，没有外链 CSS/图片，
   所以能当附件发出去，也能直接打印（有 `@media print` 样式）。
3. **别人说的话一律当文字。** 昵称和礼物名全走 `esc()` ——
   一个叫 `<img onerror=...>` 的礼物不会在文件里变成标签。
4. **文件名是纯 ASCII + 本地时间**，和日志分片、日志行对得上。

导出的范围跟着页面上选的 chip 走：看的是「最近 7 天」，导出的就是 7 天。

## 读日志缓存

战报、付费用户榜、SC 待读和对账都要把日志全量读一遍。直播中反复打开这些页面，
同一批 JSONL 会被一遍遍重新解析；几千条时是几十毫秒，几万条时能到秒级。

缓存键是「分片列表 + 每个文件的 size/mtime」，命中时直接返回已解析事件的副本。
本次进程里追加一条、归档一个分片，或磁盘上的文件被外部改动，键都会变，读到的仍是
最新的日志事实；缓存里只有事件，不会把统计结果缓存成第二份真相。

`GET /api/status` 的日志体检里能看到 `readCacheHits` / `readCacheMisses`，
用来判断是不是真的在重复读。

## 备份与版本管理

- 仓库有 git（`main` 分支）；`data/`（含登录凭证与事件日志）和 `node_modules/`
  不入库，避免把密码和运行数据提交上去。
- `data/app.json` 每次改配置前会留一份 `data/app.json.bak`；主文件被写坏时，
  启动自动回退到备份并记一条 warn，不会当成空配置把房间和插件全清掉。

## 与二代的关系

| | 二代 | 三代 |
|---|---|---|
| 定位 | 线上运行中，用户在用 | 重写中，未上线 |
| 统计 | 内存 + 定时落盘 | 日志投影，可重放 |
| 插件 | 9 个，双份副本 | 6 个，单一来源 |
| 前端 | 9655 行单文件 | 拆模块 + schema 表单 |
| 关系 | — | **不共享代码，只迁移领域知识** |

领域知识（盲盒盈亏口径、荣耀等级回落规则、连击两种报文区分）是二代的资产，
三代以「模块 + 断言」的形式重新表达，不是复制粘贴。
